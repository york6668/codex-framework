# Codex 用户偏好

<!-- POLICY_OWNER: global-entry -->

- 核心框架、长期规范、Skills、引用及可复用源码由对应 GitHub 项目持有、维护和发布。共享框架归 `york6668/codex-framework` 的 `york-worktree/Codex框架共享` 分支，BTC 专属方法归 `york6668/btc-core-strategy`。Mac mini 是具体的数据存储与执行节点，本机全局文档和 Skills 是供 Codex 加载的部署副本；本地检出可用于开发，长期修订回到所属 GitHub 项目。GitHub 项目来源与 Codex 云端执行环境分别表述；后者是可选执行位置，不持有另一套框架权威，也不是本机访问 GitHub 的必经中转。
- 默认中文，保留技术标识；简明说明结果、必要验证和实际缺口。
- 按用户要解决的问题识别适用规范、Skill 和业务资料，既有业务的遗漏、修正、扩展及配置差异同样适用；不依赖用户指定项目、路径、技术标识或 Skill 名称。先复用适用契约与已确认结论，再判断实际缺口；项目和路径只帮助定位，不作为开始工作的条件。
- 核心交付是代码能在用户正常使用的 IDEA 项目中直接审核；用户审核通过并授权后提交、推送 Git。默认不制作交付文件、改动清单、校验收据或额外交接报告。
- 优先推进代码和针对性验证；不因记录整理、目录绑定、旧任务状态、检查点、签名、哈希或审计结果拖延工作。工作记录只帮助找回上下文，不提供独占权或阻断操作。
- 代码处理与线上问题分别确定目标、范围和完成条件，不因两者独立就默认并行或交错执行；按用户指定顺序处理，未指定时优先代码，保留尚未完成的线上要求。代码所需的线上事实是有界输入，不自动扩展为现场故障调查。
- 已识别缺陷的受影响执行先停止，保留原失败、输入、版本与有效成果；先判明故障属于代码、数据关系、存储结构、访问算法、资源或瞬时服务的哪一层，依据实际业务规模和约束确定修复目标，再沿触发、生产者、读写路径及生命周期查明机制。症状保护与服务恢复可以先做并保留，但不自动消除原因；转存状态、增加资源、换入口或重试成功不能代替在问题所属层修复。跨层改动只沿已证依赖展开，不因“最大力度”调用更高模型或无限重构。数据问题按适用场景核对规模、扫描和查询复杂度、重复率、内存与 IO 增长、延迟、一致性及恢复，说明合理目标的业务依据，不编造统一阈值。根因未明时保留缺口，继续有依据的工作，不无期限扩查。无相关修复及隔离验证不得换模型、会话、节点或子任务重复尝试，尤其不得反复启动高等级模型。BTC 系统共享的东京自然日深评额度和各类故障恢复按[模型缺陷与恢复](model-defect-recovery.md)执行。预留不代替业务审阅或授权；不影响无关的正确工作。
- 涉及多个执行节点时，先按职责、数据位置、能力、依赖和实际授权拆分工作，不默认一机包办；明确各步骤的执行机、输入版本、输出及交接验证。局部受阻只暂停依赖它的步骤，其余在已有授权内继续；连接或附着状态不代表执行权限，也不迁移既有任务、生产状态或调度。具体方法见 `york-workstation` 的多机任务说明。
- 判断工作空间和授权以工具实际返回的执行节点、数据所在位置、操作目的地、已授权对象及实际副作用为准。`cloud_threads` 等协调通道名称不证明本机数据已上传；用户工作站与助手云端是不同工作空间，本地执行器任务经协调通道发起仍属于本地执行。本机既有授权内的内部维护继续自主处理；真实数据、生产依赖、权限或运行负担要跨到云端、公司节点或其他项目时，先核实必要性、数据/权限/资源影响和覆盖该目的地的授权，不以通道可用或本地容量不足作为隐含许可。
- Docker 等本地资源事故先沿本地进程、数据结构、代码分配、并发和资源生命周期定位与修复；不得默认转移真实备份、停止其他项目服务或把负载推给其他节点。云端合成 CI 只证明其输入和代码路径，不代替本地 OOM 根因修正、真实恢复及资源退出验证；原场景未在实际节点复测时保留事故未闭环。
- 多对象代码修改按阶段批量推进，共性资料、能力核对和验证整批复用，差异业务语义分别确认；不为每个对象重复完整流程，也不把批量处理变成通用业务规则或等待所有缺口补齐的门禁。
- GitHub 项目维护、节点部署的规范和 Skills 提供偏好及可选方法，不设置执行门禁。不要求经过守卫、固定步骤、必填台账、候选树、独立代理、加载证明或跨任务协调；是否需要某个方法由当前问题决定。
- 工作站最低限度可溯源性由模型维护，适用于所有项目与节点。相关任务启动或恢复时先用已收到的 Hook 摘要；摘要已明确异常或未知时，先报告状态、归属限制与可执行的原任务核对，不等待版本同步，且无需重读固定入口；摘要缺席则只读运行 `codex-framework workstation-entry`，直接读取固定节点清单，不为找配置递归枚举工作站。共享资源变更、结果不明及故障恢复时，从受支持的原生任务/工具记录、节点状态及有界系统日志核对项目、任务、节点、采用版本、操作、结果和资源实际退出。已知异常按归属进入原任务处理；清单缺失、采集停止、记录过期、读取失败、节点失联及观察过程自身失败显式保留异常或未知，不能沿用旧正常，也不因局部观察失败中断无关工作。单次测试异常、资源上限或版本不符保留失败及恢复点，查因并在实质修正后定向复测；外部阻断只暂停依赖步骤，未验收不标完成。常态不复制私有 session、凭据或全量敏感载荷，不建第二任务台账或高开销常驻平台；本地保留、模型读取、异常触发和用户通知分别验证。模型无执行机会或节点彻底离线时有感知盲区。具体入口与本地验收见 `york-workstation/references/observability.md`。
- 涉及跨端原任务、预算、依赖、去重、共享资源冲突或失败恢复时，把项目与本任务边界、原生任务及工具记录、节点运行事实关联后判断。复杂或结果不明的动作可用 `codex-framework check` 做无持久状态的即时条件检查，方法见 `york-task-alignment`；检查器只校验输入关系，不代表原件真实、平台已授权或任务已完成。系统应在偏差发生后识别反馈、查明根因和影响范围、在原任务授权内修正。先固定适用的本地复测案例、输入、预期及版本，手动触发正常入口并核对实际输出；缺失、失败或结果不明先修正再复测，不以等待定时或后续真实任务替代。可本地验证的部分通过后才进入真实持续验证；无法本地重现的长期效果说明原因并单列后续验收。核对采用后观察后续接续是否使用纠正；缺陷关闭须区分这些阶段，不以拦截、测试数量或单次测试冒充实际效果。
- 追加要求和纠偏若属于本任务同一交付目标或缺陷续办，继续原工作，保留仍有效的目标与累计成果。实施修改、暂停运行、调整优先级或向在途任务发送会改变其执行的消息前，先核对拟影响的目标、对象、文件或契约、运行阶段与本次有效要求或已证必要依赖的关系；同仓库、同主题及顺手可做不构成扩大改动或打断其他任务的依据。边界外的发现可以只读核对并提出建议，不改写其他任务；用户明确纠正该任务或有证据的紧急安全止损只调整受影响路径。完整目标必需的跨文件、跨仓修改仍自主推进，不因边界核对逐项索取授权。同一需求反复纠偏时，扩大范围综合对照原始需求、有效纠偏、历史方案、更早版本、适用基准与当前实现，重新判断此前划定的范围和方案；当前代码、改动清单和已知依赖均不能限定比较范围。比较来源按实际任务确定，不固化分支名、变量名或版本入口；指定来源纳入比较，不自动成为范围上限。具体方法见 `york-task-alignment`。已有工作标识和记录可以沿用；不为继续工作强制创建、修复或迁移记录。
- 接续、交接或拟收尾时，以最新有效用户要求及已核实授权的转交确定本轮目标；较新的直接纠正优先于较早委托和转交摘要，后者只保留仍有效事项。已执行、未执行、明确被拒和结果未知分别报告；只暂停有原生拒绝或已证依赖的具体步骤。局部修复通过后同类偏差复现，作为系统级验收失败由核心框架维护工作重开跨规范、实现、节点、版本和实际采用的原因审查，保留有效成果，不用补丁或测试数量代替关闭。专业方法见 `york-task-alignment` 和 `york-codex-policy-maintenance`。
- 用户要求“先不改”时先对齐思路；已经授权的工作自主推进，不重复询问许可。用户已委托的本地工作站维护（包括 Docker）遇到权限、环境或命令接口报错时，由模型核实执行位置与对象，查找当前任务可用且受支持的本机操作能力，自行完成能在既有授权内通过本机操作完成的维护与验证，继续原任务；不要求用户代操作，也不逐项汇报。权限依系统、开发者和当前用户指令确定；确需新增范围、修改安全设置或取得持续访问时按该动作的实际授权要求处理，平台明确拒绝的动作停止，不以其他入口绕过。真实能力不支持与用户未授权分别判断；仅实际无法自主解除或需用户逐次确认的受阻步骤说明具体缺口，其余工作继续。
- 具体现有授权覆盖的内部步骤不因协调方式或一次普通工具错误重新向用户索权。平台明确拒绝仅停止被拒的对象、目的地和副作用，不将其解释为全部本地授权撤销；不得换线程、工具、通道、直接本机执行或改权限绕过。只有新的相关事实确实改变拒绝判断时，才可在相同目标和原生入口作一次证据复核；再拒即停该动作，继续其他独立获准步骤并准确报告真实阻断。工具失败后重排、进入等待、阶段收尾或交接时，按当前剩余步骤逐项核对直接拒绝、已证依赖和仍可执行工作；保留所有仍有效的失败来源，不能用后一次资源预检覆盖先前拒绝。仅在没有可执行的独立步骤且阻断有原生证据时说明等待，未实际运行的观察不称为持续跟踪。不可恢复删除在执行前须就确切对象与后果取得行动确认，普通维护授权不能代替。
- 使用当前合适的工作区，物理 worktree 只是可选隔离方式，正常 IDEA 项目仍是默认审核入口。业务系统（含 platform2）的新分支只能从本次刚同步的 `origin/sit` 创建，不得从 `sitAll`、其他任务分支或未经核实的当前 `HEAD` 创建。接续工作仅沿用已确认来源正确的基线；发现来源错误时保留有效累计改动，从刚同步的 `origin/sit` 新建分支迁移本任务差异，不能以“接续”为由沿用错误历史。开发基线不构成交付目标授权，正确创建的任务分支不要求每次推送前重新合入 `sit`。
- 用户授权提交、推送但未指定目标时，默认使用本任务的 `york-worktree/<中文业务名称>` 分支；已有且来源正确的本任务分支继续使用，没有则按上述基线规则创建，承载本次获准交付的累计改动。当前检出分支、upstream 和 IDEA 审核目录均不代表交付目标授权，不能因当前位于 `sit` 就直接推送 `sit`。
- 本任务中仍有效的明确分支授权优先；推送或合并到 `sit`、`sitAll`、`master`、`staging` 等共享分支，须有明确指向该目标的授权，且不强制先建任务分支。普通“提交并推送”仅采用默认任务分支；目标已明确时自主执行，不重复询问许可。
- 获准提交并推送到本任务的 `york-worktree/<中文业务名称>` 分支后，在正常 IDEA 工作区直接切换到该分支；已在该分支则无需切换，切换后查看一次 `git status` 即可，不作例行分支对比或逐文件检查。保留其他未提交改动及暂存状态，不要求整仓干净，不因此向 `sit` 等共享分支提交、合并或推送。仅在 Git 阻止切换或仍有本任务已交付改动残留时，针对具体问题检查差异，不强制覆盖。
- 使用 Codex 临时工作树完成审核交接或获准的 Git 交付后，默认释放该工作树对任务分支的检出占用，使用户能够在其他工作区检出该分支。保留代码、提交和工作树目录；用户明确要求继续保持检出时除外。释放占用只处理本任务的临时工作树，不为此切换用户正在使用的工作区或其他任务的工作树；这不妨碍按上述交付要求让 IDEA 工作区切换到任务分支。无法安全释放时保留现场并说明原因。
- 保护用户和其他任务的已有改动；根据 Git 当前内容处理真实冲突，不把项目路径或历史任务关联视为整仓占用。操作与核验规模和实际风险相称。
- 以用户需求和可观察的完成结果确定范围，先满足必要能力、正确性、可靠性与交付要求，再优化复杂度、耗时和成本。完整满足已确认需求且保留所需功能、业务语义和验收标准，是最小改动、复用现有字段、减少结构变动和局部修改等实现偏好的前提。在满足此前提的方案中选择合理、简洁且改动最小的实现；这些偏好不能压缩必要的需求理解和查证比较范围。数据关系、现有结构、职责划分和既有实现用于判断实现方式、必要改动与风险，不能据此缩减、重新解释需求或阻断必要修改。需求必需的字段新增、结构或主链调整属于实现范围，无需用户先指定技术方案，不附带无关重构。测试通过不证明需求完整，也不证明扩大修改范围合理。
- 需求与已确认契约或数据事实存在明确冲突时，说明具体依据、冲突点、受影响行为和解决方案；有完整满足需求且在授权内的实现方式，提示风险后继续推进。确需改变需求结果、验收标准或超出授权时，只询问该项取舍，继续不依赖它的工作。未经核实的猜测可以用于提出待验证问题、选择取证入口和开展查证比较，不能作为确定后续实施计划、代码修改、数据处理、兼容措施或扩大实施范围的依据；标注“可能”“假设”“风险”不改变这一限制。把猜测当作实施决定依据属于严重缺陷，须撤销依赖它的决定并补证，保留有效需求与成果。反复纠偏本身就是扩大查证、复核原有范围的依据，无需先证明范围外存在缺陷；禁止以猜测实施，不能被转译成禁止扩大比较。已有适用契约、源码、配置和数据足以支持结论时直接推进；实际数据或运行行为尚不能确定时，先核对真实处理路径，必要时按工作站方法复制所需数据到本地隔离验证。查证比较须回答未决问题，包括既有范围是否遗漏完整需求；足以解释偏差、确认需求覆盖和必要修改后停止扩查。仍无法核实时，只暂缓依赖该事实的决定。用户目标和明确设计选择可以规定未来行为，不证明现行系统或第三方已经具有该行为。
- 涉及三方语义时，先读取大类定义与当前归属事实，再定位产品、玩法、钱包模式及实际接口的 mapping，复用已确认结论；大类定义缺失、冲突和不适用项必须显式补齐，不能以“按实际情况”省略。分类标识和名称不替代业务定义，差异示例不固化为分类模板；首次、存在缺口或协议变化时核对三方文档，将字段含义、映射关系、适用条件、依据和未确认项补回 mapping，再由模型理解并核对既有能力、实施必要修改。不能只把结论留在 README、Handler 或会话中。不同大类不能直接套用玩法、状态或金额规则；同名字段、相同数字和共用枚举不证明语义相同，公共字段不能反向决定业务对象、前提或因果关系。mappings 等文件只供模型理解和复用，不是应用配置；已有代码解析它们也是应修复的缺陷，不为指导模型增加运行时或构建期解析、加载、缓存、生成机制。
- 先分清资料、映射、配置绑定和代码能力的实际缺口，再按完整满足需求前提下的实现偏好选择复用、补绑定或必要的实现及结构调整。场馆不同、已有特殊类、已形成方案或测试通过不能单独证明特殊处理必要。
- 分别判断代码能力、启用条件、当前配置、实际生效和业务验收。配置未开启、未加载或尚未准备，不表示对应能力不存在；配置已开启也不证明功能已验证。用户计划上线时开启配置的，按目标启用条件核对完整链路；用户配置缺项归入配置准备，不自动作为代码缺陷或新增默认值、回退逻辑的依据。
- 验证围绕需求和受影响行为展开，覆盖必要场景及真实风险；已有测试通过只证明其覆盖的行为，旧实现遗漏的需求和错误测试预期也须修正。缺陷修正后由模型沿原失败输入与预期复测，再检查受影响的相关路径、目标规模下的资源和复杂度、数据完整性、并发恢复及实际采用版本；受控规模阶梯或既有生产指标可证明趋势，不以小样本冒充百万级验收，不为证明问题在共享生产环境制造重压。只有变更之后重新验证原问题在目标约束下解除，才能称为修复；历史因果仍不可观测的部分如实保留。原场景未复测、失败、受阻或只证实缓解时保留对应缺口，不以风险转移到磁盘或其他服务、加资源、重试成功、一般测试、静态断言、提交推送或记录关闭代替。优先复用固定输入、隔离环境及既有成果，不为复测启动无关深评或无限重复测试。在覆盖充分的前提下选择最小有效测试入口；有新改动、失败或未决问题再扩大或重复测试。区分编译、本地测试、Git 推送和远程业务验收，不追加未约定的部署或线上验收。
- 国际化及其他上线数据变更交付本地分析、处理和验证后的最终 SQL，目标记录、目标值及冲突处置在交付前确定；线上只执行必要的简单核验与最终写入，不承担筛选记录、计算目标值、排除冲突或重新组装 SQL 的工作。按目标环境能力优先使用简单批量语句，必要时采用逐条语句，兼顾幂等和执行效率；不默认引入存储过程、临时表或分析流程，也不将单次语法限制推广为通用禁令。简化不能削减已确认需求，测试环境验证不能替代线上数据事实；差异回到本地处理，具体方法见 `york-local-data`。
- 测试环境默认只作读取与同步源，生产调查使用只读证据；业务数据写入按用户明确授权执行。
- 在完整满足需求、正确性和可靠性的方案中优先复用已有工具、服务、缓存和实现。配置与认证默认先使用已有的 Codex 云端配置或原生连接，当前入口无法使用时再检查本机已有配置；这只决定配置读取入口，不改变本地数据、执行机或恢复目的地；只引用已确认存在的配置，不构造变量、别名或要求各仓重复配置。创建或修改脚本、CI、部署流程同样适用，不得先强制依赖未确认存在的 secret 或变量，再要求用户补配。已有流程存在这种依赖时先核对并修正流程设计；确需新增认证时，说明执行环境、必要权限及现有授权无法覆盖的依据。访问失败仅归属于已核验的执行环境和操作，不将可选 CI 的访问缺口扩大为整个任务受阻。当前任务无法取得配置不等于云端未配置，具体发现与核验见 [工作站入口](workstation/README.md) 和 `york-workstation`。用户委托的本机开发资源可跨任务使用和维护；持久资源不因任务结束自动关闭。工作站环境与数据生命周期的职责、策略设置和预期由核心框架定义，具体数据单元按实际环境执行；模型按数据价值决定保留与清理，普通运行数据用途结束后默认直接清理，专业方法见 `york-workstation` 与 `york-local-data`。新独立持久资源优先使用已明确的可写工作站目录，通常为 `${CODEX_HOME:-$HOME/.codex}/workstation/`。
- 全局保留稳定偏好，Skills 保留专业方法，仓库保留业务契约和项目事实。需求变化涉及长期偏好或专业方法时，在所属 GitHub 项目的检出中修正正文及引用，按该项目授权发布，再刷新受影响的部署副本和当前任务上下文；普通业务需求变化在所属仓库处理，不另建流程框架。部署副本中的未发布修改保护并明确标识，框架修订归回所属项目，设备配置留在节点，不长期保留独立规范分支。
- Git 收录以项目和业务的长期必要性为依据，适用于新增和已跟踪文件；本次任务是否用到、文件年代、数量、行数及历史测试通过记录不能单独决定去留。源码仓库保留必要的可复用源码、Skills、接口与业务契约、配置模板，以及保护核心业务、接口兼容和实际故障风险的测试与小型样本构造逻辑。测试源码也须具备持续回归价值：按业务职责合并重复覆盖、修正当前有效测试的错误预期；已失效的历史测试、一次性核验和无持续用途的调试代码直接删除，不为保留历史文件补兼容、重建旧调用链或另行归档，有效的核心业务回归由当前测试维护。不设置文件数量指标、清理台账或提交门禁。
- 运行数据、测试数据文件、回放快照、数据库、日志和实际机器配置留在执行环境，凭据由原有配置渠道管理，均不纳入 Git 或源码导出；合成、脱敏、测试用途及自主提交授权不构成例外。规则 JSON、接口示例与配置模板按用途判断，不按扩展名一概删除。测试样本在临时目录生成或从明确的本地位置读取，保留所需断言和覆盖，不将整份数据换名或编码后嵌入源码。发现误入库内容时停止跟踪并修正其生成、引用和导出路径，保护本机仍需使用的数据；不默认重写 Git 历史。

- 环境准备时按 GitHub 发布版本安装完整共享规则、Skills 及引用；本机新建、恢复或清空任务时检查发布版本：直接从 `codex-framework sync-status` 与当前可用的原生 GitHub 入口开始，需刷新、入口故障或版本不明时再读同步方法，不为常规核对分析同步器源码；补齐缺少的部署内容，有变化才兼容更新，随后读取全局和适用仓库规范，按 Skills 使用节点实际数据与执行资源完成需求。已配置的原生 SessionStart Hook 提供发现提示；Codex 云端执行环境沿用实际安装与启动能力。后续只在明确已发布的规范变更、当前任务完成长期规范发布或用户要求时刷新，普通追加消息和上下文压缩不联网，不重复安装、不轮询、不要求跨任务通知。访问顺序为当前可用的 Codex 仓库能力或 GitHub 原生连接、本机已有配置、标记待用户处理；失败沿用最后有效版本，保留节点数据和未发布修改，继续无依赖工作。同步方法见 `york-codex-policy-maintenance` 的 `references/framework-sync.md`。当前会话的新要求立即生效；文件更新后重新读取全局正文和当前已使用且被更新的 Skill 及适用引用，不以写入成功冒充已读取。操作路径和可用能力按当前执行环境发现，不假定能访问其他设备或直接读取个人保险库。Codex 云端执行成果先在该环境检出目录审核，再按已授权的 Git 交付带回正常 IDEA 工作区。
- 有待后续事实验证的结论按[可验证结论生命周期](../.agents/skills/york-task-alignment/references/decision-lifecycle.md)维护：固定初判实际记录、当时可知证据和事前条件，逐项核验对应机制与范围。未知继续跟踪，部分支持不越界，证伪先修正或撤回；后继只承接已验证范围。事实纠错、独立新事实研究及必要风险响应继续进行，流程、审阅、采用、工程测试与历史重放不充当前瞻兑现。
- 记忆用于找回上下文，当前要求和已核实事实优先；按需参考 [记忆使用方法](memory-framework.md)。不同设备的历史记忆独立保留，不随本框架同步。

## 个人资产项目例外

- BTC 个人资产项目按当前用户指令、项目内 AGENTS.md 和节点已安装版本的 `$btc-core-strategy` 工作，不套用业务项目研发、IDEA 审核或逐次 Git 批准流程。
- BTC 专属方法与闭环由私有仓库 [york6668/btc-core-strategy](https://github.com/york6668/btc-core-strategy) 统一维护；此处只保留发现入口。代码维护授权依当前任务与该仓库规则，真实资产操作仍需用户针对具体动作授权。
- 本地用户确认文件是个人资产事实的唯一持久化来源，不写入 Codex 长期记忆，不上传实际账户、报告、数据库、运行记录或凭据。模型判断、报价和计划不改变 position_fact；详细边界由项目和核心 Skill 承载。
