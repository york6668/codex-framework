# 模型调用中的已知缺陷处置

已识别的代码、契约、数据或模型产物缺陷属于执行阻断，不属于可通过换模型、换会话、续接或重试碰运气解决的瞬时失败。记录稳定任务 ID、受影响范围、原输入/版本、失败原文和已完成产物；仅停止受影响路径，无关的正确工作继续。先定位并修复，以 Sol 与隔离测试核对，再决定是否确需高等级模型重新研判。已有有效冻结结果应直接复用；同输入、无新事实和仅时钟变化不构成再次启动的理由。

BTC 交易系统的高等级深评在**整个系统**按 `Asia/Tokyo` 自然日最多启动一次，所有任务、会话、模型和节点共享。既有 BTC 节点服务的 `model.deep.claim` 是唯一权威预留入口，原子占用当天名额；失败、UNKNOWN、取消和未能确定是否启动均不退还。跨午夜在途调用计入预留日，未核清原调用前不能占用下一日。当天已完成的有效深评按真实来源复用；新事实、任务改名、模型更换和新会话均不增加当天名额。Sol 承担当天后续取证、证伪、纠错、个人适配、报告及工程维护，不把其产物冒充高等级研究。既有有效冻结研究、Owner 和报告分开保留。

故障分型后保持阻断：

- `DETERMINISTIC`：代码、契约或数据错误。先用已有证据区分止损缓解与造成原失败的机制；解除阻断须相关材料实际改变，并有绑定原失败、受影响路径及修复版本的隔离通过记录。只把状态转存、增加资源或避开触发而未解释原因时，保留缓解与未解缺口，不登记为已修复；长期分层设计能证明符合目标约束且原问题已解除时可作为修复。
- `SEMANTIC`：模型产物超出证据、范围或审批。先由 Sol 修正可机械处理的表达并独立复核；真正需要新增深评时，仍须满足原模型身份契约及当日共享额度。
- `CAPACITY`、`NETWORK`：先核实是有界的瞬时故障，还是确定性负载、数据增长、访问结构或配置导致的重复失败。瞬时故障可在实际服务恢复后解除相应执行阻断；系统性容量缺陷仍须按原规模和处理路径查因、修复和复测，服务重启、换存储或重试成功只记为恢复或缓解，不关闭缺陷。当天已耗名额不恢复。
- `PERMISSION`：只用相同范围的真实授权证据解除，不将重试或改模型视作授权。
- `UNKNOWN`：按已知缺陷阻断，先分类、取证，不自动重试。

原生 CLI 用 BTC 项目同版 `scripts/model_guard.py launch-native`，在启动前向既有节点取得 `CLAIMED_NEW`，原生轮次结束后结算；丢失响应不可重复启动。`collaboration.spawn_agent`、`followup_task` 及平台自动调用不能被本地脚本拦截：执行者须在调用前通过同一节点取得原子预留，结束后结算，未知先核清原调用。节点不可达时停止高等级调用，无本地额度替身。研究登记还须校验原模型轮次及实际内容，票据不代替语义审阅或业务授权。

既有 BTC 节点 MySQL 写入锁串行化不同任务与节点的预留，同一 `model.deep.BTC` 状态保存东京日期、原问题、阶段、调用结局及未解故障。不复制本地 SQLite 预算或按任务轮换名额。调用未知和已识别缺陷阻断其受影响执行；只凭实际改变的修复、对应隔离验证或真实服务/权限恢复解除故障，不能用次日重置掩盖。代码、运行库、日志、授权与报告分属原项目和执行节点，不纳入共享框架 Git。

高等级名额只限制启动，不证明研究完成或结论正确。BTC 项目的模型身份、结果登记、正式采用、自然报告及真实送达按原业务契约分别验收。
