# 契约、映射与 i18n

## 按语义确定责任

- HTTP/RPC、远程 DTO、事件、共享类型和外部消费的序列化载荷构成共同契约；内部局部参数不自动升级为共同契约。
- 按具体语义问题区分事实或分类来源、结构含义、序列化动作、派生值及默认/资源选择，分别确定语义责任方、结构责任方、生产者和消费者。
- 共同字段涉及三方原始语义时，按当前问题判断是否需要 [发现和读取三方资料](../../york-provider-docs/SKILL.md)。外部约定与平台转换分别有其依据，不能从消费代码反向定义三方协议。
- 沿 Controller、DTO/VO、调用或事件定义、映射、持久化与真实消费路径确定责任；仓库名、共享字段、辅助方法或最终输出相同不证明这些问题属于同一个 Owner。
- 新增校验或处理层前，查明既有链路已建立的保障、实际适用条件和数据，定位需要满足的具体缺口。跨线程、信任边界或时效变化须有实际路径及条件支持，才能据此决定补充校验；仅设想保障会失效只能形成待验证问题，不能据此添加兼容、回退或重复检查。
- 在完整满足需求的方案中，优先扩展能够承担职责的既有组件。需要调整结构或职责边界时，保留需求所需的业务含义，核对事实来源、适用条件及消费者差异，按需求设计转换并处理兼容影响；不能把现有边界当作需求限制，也不为测试便利扩大生产职责。

## 核对受影响维度

- 对变化的边界核对字段名、路径/嵌套、类型、格式、必填、缺失与 null、默认值、枚举、单位及业务含义；只记录本次相关维度。
- 稳定 code、公共枚举或业务语义变化沿生产、映射、存储/事件、消费和最终输出追踪，包括异名和间接消费者。字段全文检索是入口，不能单独证明影响已覆盖。
- 异名映射明确 source → target 的方向、转换、空值/异常行为、兼容理由和代码锚点。没有对应证据时，先查清契约，避免静默添加别名或默认值。
- 重命名/删除、类型/路径、必填、null/默认、枚举或单位含义变化需分析消费者兼容；由已核实的消费方式、数据及有效目标决定是否需要兼容措施，再按真实责任和依赖顺序修改契约、实现及测试。不能仅凭“可能影响消费者”预定双写、回填、别名或额外对比；静态材料不能区分实际影响时，补取能回答该问题的必要数据或隔离验证。
- 共同契约依据当前有效需求确定目标变更，从目标版本的代码和测试引用字段定义，不在多个仓库或方案中复制另一份定义。发现漂移时修正对应责任处，待实现或未确认的部分如实标明，不凭未核实的假设补全协议字段。

## i18n 与业务事实

- 分别核对生产写入、持久化读取和消费展示。状态、类型和第三方原码保留其稳定业务表示，在既有消费边界派生 i18n key 或文案，避免用展示值覆盖业务事实。
- 已有字段契约本身是 i18n key 时，保持其类型、空值与兼容语义，并以源码和契约测试核验；不机械套用新的存储规则。
- 新增或修正展示 key 时，核对配套字典 SQL 是否一并交付；代码与 SQL 复用同一份已核实映射依据。交付目录、语言和环境范围遵循当前任务与项目契约，不把某个场馆的约定推广到全部业务。
- SQL 交付遵循 [本地分析与最终 SQL 交付](../../york-local-data/references/data-sync.md#上线-sql-的本地分析与交付)，优先采用目标数据库支持的简单批量幂等写法。MySQL 可在核实完整唯一键及排序规则后使用多行 `INSERT ... ON DUPLICATE KEY UPDATE`，通常每批约 500 条，按执行平台限制调整；平台限制或本批变更需要时采用逐条语句，不默认引入存储过程、临时表或会话控制。
- 必要的索引、重复键、大小写及关联冲突检查，由模型依据只读取得的数据在本地分析，交付前确定记录、目标值及冲突处置，并验证最终 SQL 的实际结果、重复执行及历史数据兼容。线上仅做已准备好的简单核验和最终写入，不承担分析、筛选或改写 SQL；发现数据不符时回到本地处理。分别说明本地 SQL 验证、代码验证与远程生效状态。

## 验证

- 契约测试针对受影响接口、消息或序列化边界，分别验证来源/分类、消费者选择、结构转换与最终输出。单一 DTO、相邻接口或另一数据链通过不能代替这些断言。
- 对破坏性变化覆盖旧/新消费者、缺失/null、异常映射和关键单位或枚举场景；明确实际执行及尚未验证的边界。测试方法使用 [Java 验证](../../york-java-test/SKILL.md)。
