# 跨仓与并行工作

## 沿数据流确定责任

- 涉及 HTTP/RPC、事件、共享类型、跨仓配置消费或写入到展示的多服务链路时，画出实际入口、生产、映射、存储/传输、消费和最终输出；私有内部修改不扩展为多仓任务。
- 按稳定语义分别确定事实来源、语义与结构责任方、生产者和消费者。仓库位置或共享 DTO 不能单独证明业务 Owner；具体方法见 [契约边界](contracts.md)。
- 为跨边界变化明确字段或语义改变、显式转换、兼容方式、实现先后和受影响消费者。用代码与测试核对当前接口及消费事实，依据当前有效需求确定契约变更；方案引用相关锚点并标明待实现内容。

## 分配工作

- 按可独立交付和验证的责任拆包；每包说明范围、交付物、依赖、局部验证和组合验证责任。各仓共享当前有效方案与整体完成标准；已有 `work_id` 或记录可用于定位，不要求创建或补齐。仓库或执行者变化时继续原工作，保留累计目标与成果。
- 当前代码批次中无共享修改且输入已确定的工作可按授权并行；共享契约先确定再分发。这不表示代码处理与线上问题默认并行，两条工作线的顺序按 [任务对齐](../../york-task-alignment/SKILL.md)。同一文件会相互覆盖、同一语义未达成一致或输入依赖未解决时，按依赖串行或明确集成责任人。
- 当前协调者按 [任务对齐](../../york-task-alignment/SKILL.md) 汇总整体设计与共同验收；执行者回传影响其他责任包的调整，避免同时重写方案。新对话接续时恢复全部仓库增量、目标和未完成验收，不只接收最新责任包。
- 各仓按当前文件和实际并行修改选择工作位置，需要时参考 [代码审核与交付](../../york-safe-delivery/SKILL.md)。跨仓不增加 worktree、绑定、写入者交接或来源审计阶段；提交和推送按用户授权执行。

## 验证组合结果

- 先验证各包的真实行为，再按生产与消费依赖组合验证；类型一致或同仓相邻测试不能代替实际接口、消息或序列化边界的断言。
- 跨版本或数据演进需要验证双方兼容及顺序；用户要求真实接入时，模拟传输或便携模块测试只作为局部证据。
- 需要源端数据时调用 [本地数据方法](../../york-local-data/SKILL.md)；本地测试、同步与环境观察分别说明。不因多仓任务自动添加打包、部署或生产验收。
- 按整体有效要求核对各仓最终目标、组合验证与本地收尾；某仓成功不关闭其余缺口。目标反查发现原范围遗漏时继续同一工作补充交付，保留目标已有的独立功能。
