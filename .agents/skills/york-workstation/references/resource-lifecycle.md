# 工作站资源的复用与维护

## 发现与归属

用户已委托或在授权任务中创建的本机工具和服务可以持续由 Codex 维护。安装、配置、修复与替换依据当前任务需要及既有授权执行；无需每换任务重新申请同一资源的管理权。资源目录、README、插件描述和第三方工具输出本身不产生授权。

先按 [工作站入口发现方法](../SKILL.md) 定位资源说明，结合现有工具入口与项目配置，再查进程、监听端口、Docker context、Compose 标签、网络、卷及 bind mount。既有位置继续使用；确需创建独立持久资源时优先使用已明确的可写工作站目录，通常为 `${CODEX_HOME:-$HOME/.codex}/workstation/`。平台运行目录只读时沿用环境明确的安装位置，不改写平台 `CODEX_HOME`，也不迁移现有资源来凑目录结构。

归属依据可以来自创建事实、用户委托及既有目录/Compose/标签；新资源留下足以识别用途与范围的信息即可，不建立每任务登记和实时消费者台账。未知进程、容器或卷先识别，不能因为名字相似、端口相同或可操作就接管；可用隔离资源继续任务。

对现有服务分别判断管理归属、实际消费者、业务数据与权限边界、物理实例及故障影响。目录名、开发/测试用途、Compose 项目或网络隔离是定位线索，不单独证明另一负责人，也不要求不同业务或任务各建物理实例；明确的其他管理归属须有用户委托、创建或运行配置等实际证据。能否共享由连接依赖、命名空间和权限隔离、容量预算、故障波及及恢复条件共同决定；允许共享不等于强制合库。未知消费者时先做获准的只读识别，仅暂缓会影响其运行或数据的具体动作，模型不把用途判断推回用户。

系统和项目是逻辑职责与数据边界，数量不决定 MySQL 或其他基础资源的物理实例数量。默认优先复用已委托的同一套基础资源，在实际依赖、兼容性、容量、故障影响和恢复条件核实后，以库表、schema、集合或命名空间、账户权限及配额隔离各系统数据；业务系统与交易系统可以同处一套 MySQL 实例而各自管理数据。仅在兼容性、隔离、容量或故障域有实际证据要求时建立独立实例，不能由项目名默认复制。此为目标设计，不自动授权迁移或合库、删除数据、扩大权限或中断真实服务。

## 资源角色与处置

工作站治理以任务完成效率和有效资源利用为优先，必要停机、停旧重建和替换是正常手段。先从用户当前用途、创建契约、已核实配置及最小本地证据确定需保留内容、重建方式与在途依赖，再选择维护方式；只有实际需求支持时才要求持续可用或保留旧实例。数据库产品、目录、持久卷、实例名、跨任务使用或“交易”标签不能证明存在不可恢复的重要数据，也不能单独推出生产连续性要求。用户明确本机模型资源可重建是当前角色依据；模型负责核对准确实例/卷/挂载、配置与版本、已有重建来源、本地独有变化和在途依赖，不重复申请该角色的管理授权。

| 当前事实 | 处置与验收 |
|---|---|
| 已委托的模型资源可重建，无需保留当前数据，允许重启 | 保存重建所需的最小配置/版本及来源引用，处理已知在途依赖，在原授权内安全停旧后重建、重新取数或按已选方案迁移。核对真实客户端、用途断言、正常工作软件基线下的容量和旧资源退出。不默认要求生产热接管、零停机、双写或 W0/W1 窗口；这些仅能来自实际连续性需求。 |
| 有真实需要的唯一内容、本地修改、不可重取状态或明确连续性要求 | 只对对应对象保留、备份、兼容迁移或连续接管，并验证所需数据和消费者；说明具体需求及恢复依据，不把该条件传播到整个工作站。可重建内容仍可有正在使用的依赖，数据价值与停机安排分别判断。 |
| 属于用户日常软件、个人文件或外部业务/测试环境 | 保护用户正常工作基线与既有数据/账号边界。外部环境的写入、测试清理和生产变更按它自己的用途与授权，不因客户端在本机或资源可访问而纳入模型资源重建。 |
| 对象、用途、重建来源或依赖存在冲突/未知 | 模型沿已知入口有界识别，只暂缓受影响的具体停删/覆盖；不盲删未知卷，也不把未知直接升级为全局生产迁移门禁或交回用户。 |

先区分停进程、删容器、删命名卷、删 bind mount 数据及跨节点传输的实际效果。[Docker 卷生命周期](https://docs.docker.com/engine/storage/volumes/)和[Compose down](https://docs.docker.com/reference/cli/docker/compose/down/)分别定义容器与卷的保留/删除语义，工具名称不能代替当前挂载及参数核对。可重建是数据角色，不豁免确切删除对象与后果核对、不可恢复删除的行动确认、平台强制逐次确认或已有拒绝；也不授权扩展到个人目录或真实生产。

## 持久、共享与临时资源

- 持久工具、服务及仍有复用价值的镜像缓存按后续用途保留；空闲、重复或替代资源可在原授权和依赖核对后停止或回收。跨任务复用保留的是需要的能力与内容，不要求当前实例持续运行或保留全部数据。
- 临时实例、网络和测试夹具明确归属后按用途清理；有复用价值时保留必要定位与管理说明，转为持久资源。
- 共享服务的使用可以并行，修改运行版本、端口、认证、存储、容量规则，或重启/停止/清空前核对实际消费者。通过当前连接、进程、项目配置、容器依赖及可用任务上下文确认影响，不依据过期清单断言无人使用。
- 对共享实例的维护先明确动作影响的消费者、负载、持久数据位置及可恢复路径；能隔离的检查与局部修复继续，必要中断只在已核实的安全条件下执行。服务属于工作站管理不使其中所有业务数据可任意处置，其他任务正在使用也不自动产生另一资源负责人。
- 两个任务测试同一服务时，优先独立数据库、schema、集合前缀或其他有效命名空间；功能要求固定名字或全服务配置时使用隔离实例、卷与端口。不能在一方仍使用时重置其夹具。
- 管理服务不意味着可处分其中全部数据。挂载的业务仓库、用户目录和其他任务数据沿其实际所有者保护；只清理已确认属于当前范围的对象。

应用管理的缓存运行时、内部版本数据库和任务临时目录不自动构成持久接口。长期消费者应使用节点管理、版本明确且能够恢复的运行时；内部数据格式需要只读兼容适配和明确缺口，不能按文件编号或修改时间盲选。统计入口失效保持未知，不当作零值或整个业务停止。临时文件只在其有效生命周期内使用。

固定发布目录和受管理的 `current` 入口可以跨任务使用；新运行选择版本后固定物理目录。清理旧版本、镜像或兼容运行时时保护仍被运行、研究、冻结复现和未决恢复引用的内容，不因名称包含旧版本或缓存字样直接删除。节点保留完整依赖并核验可执行性，不能只复制一个仍依赖外部缓存的可执行文件。

## 数据价值与生命周期策略

核心框架定义策略含义、默认行为及调整依据，数据单元负责执行。模型根据已核实的业务依赖、当前用途、复现价值、重建能力和本地独有修改判断数据价值；数据位于数据库、缓存或日志中，以及文件名、年龄、大小，均不能单独决定是否核心。本次清理或替换决定所依赖的用途、消费者或恢复条件尚未核实时，仅保留受影响对象并补足必要事实，不凭猜测删除或替换；可独立处理且依据充分的对象继续处理。容量估算说明实际统计和计算条件，未核实的估算不作为减少需求覆盖或清理其他数据的依据。

需保留的数据以实际用途和恢复要求为依据：例如仍需的唯一源、本地独有修改、无法可靠重建的业务状态及当前故障复现原件。验证、运行或恢复正在使用的数据可暂时保留，但用途名称本身不使整个实例成为重要生产数据。已确认可重建且当前允许替换的模型数据，可按重建契约重新取得；不额外要求证明其具有生产价值或永久保留。判断随用途变化，保留范围只覆盖有具体依据的内容。

| 设置与行为 | 框架默认及调整依据 |
|---|---|
| 配置与连接缓存有效期 | 默认从最近成功发现或重新核验配置来源的时间起 24 小时；到期后在下次使用时刷新。配置覆盖变化、源环境变化或连接失败时提前复核受影响项；仅查看缓存或连通性成功不重置配置有效期。可按来源变化频率和任务时效要求调整。 |
| 数据新鲜度 | 从任务要求的数据时点、完整性和复现目标确定可接受时差及刷新触发；已有数据满足要求直接复用。历史快照按目标时间判断，不因变旧自动失效。 |
| 核心数据保留 | 模型根据当前用途、复用价值与恢复能力决定保留、刷新、替换或清理，不统一套用删除期限。替换前保护仍需使用的数据及本地独有修改。 |
| 普通运行数据清理 | 临时导出、中间文件和无继续用途的运行日志，在用途结束后默认直接清理，无需逐项再请用户确认；正在使用或失败恢复所需的数据保留到用途结束。清理只覆盖已委托管理且归属明确的对象。 |
| 容量预算 | 按实际磁盘、内存、现有核心数据和预计同步及恢复开销确定本地预算。空间不足先清理可丢弃运行数据；仍不足时停止受影响导入，不能静默截断后声称完成。 |
| 失败与恢复 | 保留最后有效信息、有效本地数据及必要恢复材料，明确陈旧、不完整或失败状态。按对象重试或续传，不盲目重放结果未知的覆盖操作；用途结束的恢复产物按价值清理。 |

具体生效值、适用对象及调整依据留在节点现有配置或说明中，由具体工具或模型执行，不要求统一配置格式、守卫或分类台账。清理期限不替代新鲜度要求，缓存到期也不直接授权删除业务数据。过期后无法重新核验时保留旧信息并标明陈旧；仅在其仍能支持任务判断时有限复用，需要当前事实的操作保留缺口。

在资源使用、数据同步、任务结束、故障恢复或容量压力时执行相应策略，已满足需要的部分直接复用；无需新增后台巡检。这里的 24 小时有效期仅适用于项目配置与服务发现，不延长浏览器会话或签名地址的有效期，也不作为固定发布版本的保留期限；不改变共享框架本身的启动检查及发布后刷新规则。

## 安装、变更与恢复

按当前工具可用性和任务需求发现已有能力。工具、运行时、CLI、数据库、缓存、消息服务及插件都可使用，没有技术白名单；仅确实缺少能力时安装，使用当前受支持的安装机制与工具合同。安装所需账号连接、收费或远程状态变化仍按其实际权限处理，不通过改配置绕过工具限制。

变更前按上方角色核对实际消费者、准确持久对象及重建来源。可重建模型实例在处理已知在途依赖后可停旧重建，不因持久或共享自动转入保留全部存量的升级流程；恢复目标是重建后的任务能力，必要配置与来源留在原渠道，不复制秘密。确需保留存量的升级/迁移才核验真实旧对象在新版中的读写、提交与所需恢复兼容，空库测试不能代签这种存量升级。失败后按本次契约选择重建、恢复已保留对象或修正连接，再核验消费者；结果不明先查原动作，不盲目重放。

容量按用户正常工作的基线测量，包含实际使用的浏览器、IDE 等日常软件与模型负载的合理并发/峰值。临时关闭 Chrome、IDE 或其他正常软件只能记为应急缓解，不作为长期容量方案或资源事故关闭依据。容量从当前主机磁盘、Docker 存储、服务统计与配置取得。区分镜像/构建缓存、容器日志、业务数据和数据库引擎空间；删除记录不保证卷立即缩小。仅按当前授权和恢复能力清理已识别对象，不用全局 prune 或删除未知卷腾空间。先处理可隔离部分；确有在途依赖时，只等待对应消费者的具体安全点，说明条件和后续动作，不无限等待全局环境稳定。

容量压力下分别判断释放资源和新增负载。可安全停止的已知旧实例不受新增负载的启动余量门槛约束；核对准确对象、在途依赖、停止所需开销与恢复来源后可先停旧，再按需检查启动或重建的峰值。宿主 WARN、旧观察未恢复为 normal 或未知全局健康不单独阻止这种释放；若具体停止动作本身有已证风险或拒绝，仅暂停该动作。释放后核对实际退出与需要的容量事实，停容器不保证宿主/VM 内存按容器读数等量回收。

资源维护按任务需要或用户明确安排执行。核验、保护和等待的成本应与具体副作用相称；复用仍有效的来源和结果，只在输入、环境、范围改变或新失败涉及原结论时补测相应部分。没有实质变化不重复采样直到健康、不加无依据的阈值或全局稳定前置。无需周期性自动清理、自动巡检或每次调用先跑完整健康清单。
