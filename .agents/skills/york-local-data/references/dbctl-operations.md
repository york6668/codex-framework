# 本机数据准备与同步操作

需要本地调试数据时，先复用已有数据、管理工具和操作记录。先从当前设备工作站入口定位工具；`$HOME/docker/mi-local` 仅是可核验的发现线索，路径或工具缺失时再从 Docker Compose 标签、相关脚本和本机记录定位。它目前支持的服务是该工具的范围；新组件准备按需使用 [工作站](../../york-workstation/SKILL.md)。

## 找到现有入口并区分副作用

先读 实际工具目录中的 `README.md`，具体容量、逐对象分类和版本以工具当前配置与代码为准，不复制成全局默认。`dbctl` 自带 `.venv`，不必先在全局 Python 安装同一套依赖。

| 需要 | 从工具目录运行 | 实际行为 |
|---|---|---|
| 服务状态 | `./dbctl status` | 读取 Compose 状态。 |
| 容器日志 | `./dbctl logs <服务>` | 读取该服务最近日志。 |
| 已有同步摘要 | `./dbctl report` | 读取运行记录；不能代替当前数据核验。 |
| 当前容量 | `./dbctl capacity` | 读取本地数据库统计和容器卷使用量，覆盖现有服务。 |
| 同步参数 | `.venv/bin/python scripts/sync.py --help` | 只显示同步帮助；`dbctl sync --help` 会被外层解析器接管，只显示总帮助。 |
| 更新源对象清单 | `./dbctl inventory` | 源端只读，本机会更新 `state/inventory.json` 和 `config/sync-rules.json`。 |
| 工具测试 | `./dbctl test` | 含本地数据库写入、恢复及清理夹具，不是只读健康探测。 |
| 启动已有环境 | `./dbctl up` | 启动 Compose、必要时初始化本地 Mongo 副本集并完成就绪检查；已有服务可用时无需重启。 |

连接参数由 `config/test.json`、`config/local.json` 和本地凭据文件提供；按需读取相关字段，不打印密码、令牌或整个配置。先核对当前 Docker context/endpoint 与 Compose 项目标签；远程 daemon 中的同名容器不代表本机资源。工具的 `guard_local` 检查项目、运行状态和端口绑定，不能代替 daemon 位置核验。

## 为所选验证准备数据

- 数据依赖由所选验证和实际读写路径决定。配置、映射或关联记录只在相关路径会消费时准备；涉及查询或写入语义时，核对对应字段、类型、索引和约束，避免用不完整数据解释业务行为。
- 复用满足要求的已有数据，按相关差异补充；需要隔离或对照时，再选择当前任务的独立库、集合或夹具。补一个字段或映射不意味着需要全量同步，对照样本也按待区分的问题选择。
- 缺项影响所选验证时，可从授权源只读补齐、构造标明假设的条件夹具，或改用能够回答问题的其他证据；只暂停依赖缺项的操作，独立工作继续。当前配置或快照不能冒充事发时缓存，夹具行为不能冒充现场结果。

## 选择数据并执行

- 从待验证行为确定实际源环境、业务库、表或集合及时间范围。读取当前 inventory、逐对象规则和相关运行记录；已有数据满足断言时直接使用，不为每次调试重做全量同步。
- 工具使用测试连接读取源数据、本地连接承接写入。核验目标与源身份不同，以及本地应用最终连接没有通过环境变量、profile 或默认值回退到源端。启动初始化、调度、消费者及回调也属于实际连接检查范围。
- 涉及站点动态数据源时继续查实际加载链。游戏中心已有 `DynamicDataSourceFromDBProvider → MasterControlApi.loadDataSource` 入口；仅改示例 JDBC 或 application YAML 不证明最终站点连接已指向本地。按本次业务核对实际站点与库，旧 inventory 的其他站点结构不能替代目标表。
- 优先明确服务和对象。下面的库、对象与时间均由本次任务和当前清单确定：

```sh
./dbctl sync --service mysql --database <实际库> --table <实际表> --days <天数>
./dbctl sync --service mongo --database <实际库> --collection <实际集合> \
  --from <含时区起点> --to <含时区终点>
```

- `--database`、`--table`、`--collection` 可以重复；表要求 `--service mysql`，集合要求 `--service mongo`。只给库而不指定服务，会匹配 MySQL 和 MongoDB；不会处理 Redis。
- 基础对象按现有规则全量复制，历史按时间及容量限制，未知历史时间的对象可能仅结构；活动可能是有限样本。`--days` 不改变基础对象分类，样本不证明完整时间覆盖或跨集合关联完整。具体预算读取当前 `config/capacity.json` 与 README。
- Redis 当前工具只支持 `./dbctl sync --service redis`，会替换本地 DB 0；没有按 key 同步参数。不要把它作为查询命令。
- 同步会直接替换所选本地表或集合，工具不自动创建覆盖前备份。按当前任务的本地数据范围调用，其他工具、目录和任务的数据处理边界仍按实际对象判断。
- `--full` 虽可能出现在帮助中，当前实现已拒绝该选项。范围不匹配、规则缺失或容量不足时保留具体错误，不能通过删规则、换源或扩大同步范围绕过。

## 核验当前运行与恢复

同步结束后回读 `state/runs/<实际 run-id>/run.json`：核对选择范围、固定时间窗口、对象状态、实际记录数、错误，以及 `truncated`、`limit_reason`、窗口校验等对象字段。对本次选择的数据核验必要结构、类型、索引、窗口边界和样本，再运行目标业务断言；同步成功、容器健康与业务验证分别判断。

报告 `reports/<run-id>.md` 是该次执行快照。测试源同步期间可变化；工具不提供跨表、跨服务原子快照。对源端抽样发生变化与本地导入损坏分别判断，不能只比较两次不同时间的总数就宣布一致或损坏。

`scripts/verify.py` 面向首次完整导入，包含固定版本、全量清单和指定基础对象检查，默认 run 也可能是旧运行。不要直接套用到任意选择性同步；它还会写验收报告。复用其中方法时，按本次范围核验，保留具体原始结果。

需要恢复时读取当前 run 与错误，使用：

```sh
./dbctl sync --resume <实际 run-id>
```

- 续跑沿用原源配置、范围、时间窗口及规则快照；不要附加新选择器或新时间。源连接、容量策略或范围改变时按工具要求建立新运行。
- MySQL 失败表重新导入；Mongo 基础对象按检查点续传，容量受限历史对象按其恢复实现重导；Redis 重试重新覆盖 DB 0。已完成对象会跳过，不能通过手工改 `status` 伪造恢复。
- 原运行和统一容量锁用于防止并发争用，不能删锁绕过仍在运行的同步。容量或磁盘问题解决后再恢复对应对象；不将失败扩散为其他本地验证的统一阻断。

需要展开实现时，读取 实际工具目录中的 `scripts/common.py`（连接与目标保护）、`scripts/sync.py`（同步及恢复） 和该工具测试；不要把整套源码设为每次调用前置。
