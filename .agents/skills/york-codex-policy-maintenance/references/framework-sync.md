# 任务启动同步与明确变更刷新

共享框架、长期规范、York Skills、引用及分发源码由 用户已确认公开的 GitHub 仓库 `york6668/codex-framework` 持有、维护和发布，发布分支固定为 `york-worktree/Codex框架共享`。Mac mini 是实际数据存储与执行节点，全局文档和 Skills 是部署副本。BTC 专属方法归 `york6668/btc-core-strategy`，不由本共享同步器安装或覆盖。

任务新建、恢复或清空时检查 GitHub 发布版本，补齐缺失部署、兼容更新变化，再读取适用规则并使用节点实际数据与工具完成需求。后续只在用户要求、当前任务完成长期规范发布或收到明确的已发布变更信息时刷新。普通追加消息和上下文压缩不联网，不设置轮询或跨任务通知。当前用户指令立即生效，读取到的框架不能覆盖更高优先级要求。

GitHub 项目是内容来源，Codex 云端执行环境是可选运行位置。读取 GitHub 不要求中转到另一个任务，也不以发布 Codex 环境为前提。本工具保留的 `--cloud-error`、`cloud_error` 和 `route=cloud` 是原生访问入口的兼容字段，不表示内容由 Codex 云端执行环境持有。

## 读取来源与应用

命令入口为 `$HOME/.local/bin/codex-framework`，启动提示使用安装时确定的绝对入口及目标参数，不依赖终端 PATH；显式安装到其他 Codex home 时沿用 `--codex-home <安装目录>`。普通启动先消费 Hook 已完成的实测结果，不重复联网或安装；结果缺席、未知或明确仍有待办时，按下列命令与已支持的远端入口补核；只有入口异常或确需修改同步器时才检查实现源码，不先读取或解析整套工具代码。已收到的工作站异常摘要可先用于首报，版本核对不阻断其可执行处置。先执行 `sync-status`，保存返回的 `expected_revision`，作为本次读取远端前的版本。它只用于防止并发同步覆盖较新的内容，不提供任务独占权。

优先使用当前任务可调用的 Codex 仓库能力或 GitHub 原生连接，直接读取 GitHub 发布分支。当前 GitHub 连接可通过 `github_fetch` 读取 `https://api.github.com/repos/york6668/codex-framework/branches`，从中选取上述精确分支；避免把含 `/` 的分支名整个编码后当作单段 URL。工具可用性按当前任务发现，不要求固定工具前缀。

取得完整提交 SHA 后执行：

```sh
"$HOME/.local/bin/codex-framework" refresh --revision <刚读到的SHA> --expected-revision <先前返回值>
```

- `current`：发布版本未变，不获取整套文件或重复安装。版本记录不证明部署文件完整；用 `status` 对照该发布内容、共同基线与本机文件状态，读取所需正文及引用时核对文件实际存在。缺失文件被判为可更新项时，从已核对的该发布版本缓存或检出中补齐；`keep-local` / `conflict` 保留差异并核对具体内容，不能只凭文件缺失推定用户删除、安装失败或应当恢复。原因未知时保持未知，继续可独立完成的更新，不整套覆盖。本机修订按下节区分归属，不将其当作已发布规范。
- `snapshot-required`：在同一个 SHA 读取递归 Git tree，以及同步范围内的全部文件。可用 `github_fetch` 读取 `/repos/york6668/codex-framework/git/trees/<SHA>?recursive=1`，`github_fetch_file` 的 `ref` 必须使用该 SHA。并行读取独立文件；任何必要文件读取失败，不拿部分内容当成完整发布版。
- `superseded`：其他同步已更新版本，本次没有覆盖；读取当前已安装规范即可。不连续重试或阻断业务。

把工具实际返回的树和正文写入临时 JSON 文件，再执行 `refresh --snapshot <临时文件> --expected-revision <同一先前返回值>`。JSON 格式如下，实际文件内容来自仓库，不能照抄占位值：

```json
{
  "source": "https://github.com/york6668/codex-framework.git",
  "branch": "york-worktree/Codex框架共享",
  "revision": "完整40位提交SHA",
  "truncated": false,
  "tree": [{"path": "仓库相对路径", "mode": "100644", "type": "blob", "sha": "该文件的Git blob SHA"}],
  "files": {"仓库相对路径": "完整UTF-8正文"}
}
```

`tree` 使用实际完整递归结果，可保留范围外的元信息；`files` 只包含同步器允许的共享正文，且与树中允许的文件集合完全对应。允许范围为 `.codex/AGENTS.md`、记忆框架说明、记忆配置示例、工作站 README，以及同步器固定的 York Skills 下的 Markdown/YAML；排除其他 Skill、配置、设备说明、记忆、业务数据、运行状态和凭据。树被截断、缺文件、正文不符、异常路径或链接都会拒绝应用。同步器源码和测试留在维护仓库，不从快照直接执行或复制到用户配置。

原生入口不可用、无权读取或内容取得失败时，执行一次：

```sh
"$HOME/.local/bin/codex-framework" refresh --cloud-error '本次实际访问缺口的简短说明' --expected-revision <先前返回值>
```

只记录错误类别，不填凭据、认证 URL 或整段原始日志。同步器通过维护仓库已有 `origin` 和本机 Git/SSH 配置回退，fetch 限时 10 秒，不弹认证输入、不切换分支、不合并工作区、不新建凭据。每个入口失败后转下一入口，不重复相同请求。Codex 云端任务列表失败不证明 GitHub 连接不可用；本机缺少同名变量不证明 Codex 云端未配置。两个入口均失败时，同步状态保留最后有效版本并标记 `pending-user`，节点数据与未发布修改保持原样；`notify=true` 才提示用户，同一状态不重复提示，继续不依赖刷新的工作。

## 冲突与当前任务生效

同步沿用每文件共同基线、锁和写前复查。部署副本的单方修订保留为 `keep-local` / `local_overrides`，明确属于未发布修改；双方修改同一文件则报告 `conflicts`，其他独立更新仍可应用。`observed_revision` 表示最后取得的版本；`applied_revision` 只在全部可合并时推进，不能把部分同步说成全部完成，也不能据此将保留的本机差异说成 GitHub 已发布内容。

差异按用途处理：框架正文与方法修订归回所属 GitHub 项目；实际设备配置归回节点 `workstation/local.md` 或原有配置渠道；运行数据、历史记忆和凭据留在执行环境，不进入框架。未发布修订保护到合并、发布或按用户要求处理为止，不长期作为独立规范分支。来源不可用时沿用最后有效版本，按当前有效用户要求处理保留的修订，不把恢复发布当作无依赖工作的门禁。

发布内容缓存到安装目录的 `framework-sync/upstream.json`，供冲突对照和默认 `status` / `apply` 使用；缓存与同步状态都是节点运行数据，不进入源码仓库。`--repo` 显式指定时用于维护者比较和应用本地源码，这属于开发验证，不能把未发布修订或较旧检出误当最新发布版。

首次迁移没有基线时，由当前任务逐项兼容合并已存在的规范，保留有效偏好及 BTC 例外。长期修订归回所属项目并发布，未发布部分继续标识和保护；不能通过伪造基线跳过真实冲突。解决冲突后，以对应的真实发布快照再次刷新即可推进基线。

更新后读取实际安装位置的全局 `AGENTS.md`；当前任务已使用的 Skill 若被更新，读取相关正文和适用引用。新建、恢复任务也读取适用仓库规范。同步输出中的 `changed` 仅代表文件已更新，不证明模型已读取；不创建加载收据或把读取确认作为业务门禁。

## 长期修订与发布后的刷新

在所属 GitHub 项目的检出中修改正文、Skills 和引用；若修改先发生在部署副本，可将确认的框架差异带回维护检出，`export` 仅提供这一能力，不承担提交或发布。按所属项目授权完成必要验证和 Git 交付，读取 GitHub 发布分支及正文确认结果，再用该发布版本刷新受影响的节点副本。BTC 项目按自身授权和分发方式处理，不扩大本同步器范围。

验收按本次目标分别核对 GitHub 正文、实际安装入口与当前任务的使用：明确来源权属和更新方向，核对当前上下文实际取得的全局及适用 Skill，并在实际需求中采用。若发布针对已发现缺陷，在实际采用版本下复测原失败行为和受影响路径；只完成发布与文件比对时保留行为复测缺口。需要验收正文变化后的启动更新时，保留真实已部署旧正文及待测运行程序，由所属仓库发布有效正文修订，再从目标宿主的正常入口触发，核对同一原生回合的发布结果、部署变化、Hook 注入正文和模型实际读取与回答。提前手动刷新、直接调用 handler 或借用旧运行程序的成功记录，都不能代替该现场；原失败与修复后的结果分别保留。无变化启动、正文更新、程序升级各按实际发生范围说明，不为验收制造无业务含义的正文标记。

核心框架修订由实施任务冻结候选并完成开发自测，另由独立任务在确定的代码、数据或脱敏夹具、环境及验收标准下验证对应范围。独立范围通过后按已有仓库授权及时发布并刷新受影响安装副本，不因其他系统仍在实施而扣住该范围；失败保留结果、交回实施修正，再验证确切新版。发布与安装结果不倒推独立验证已通过，也不代替原任务真实采用和长期效果。

## 启动 Hook

安排生命周期现场验收前，先核对目标宿主的实际版本、官方入口说明及当前工具合同。优先使用已获准的原生任务入口完成发起、恢复、等待和核收，用户操作作为缺少适用入口或必须原生信任/确认时的兜底，不作为固定执行方式。桌面控件控制受限与原生任务工具能否使用分别判断；核对被拒的准确动作、对象和副作用，不把局部控制限制扩大为全部任务能力不可用，也不通过换工具、私有协议或直接调用 handler 重放被拒动作。

已有明确发送授权的验收聊天，可先用 `read_thread` 核对目标、状态和旧回合，再用 `send_message_to_thread` 发送范围内的只读核对问题，由 `wait_threads` 等待后读取原生事件、注入和实际回答。已加载聊天的普通追加不保证产生 `resume`；未加载状态也只是选择候选的依据，须由实际回合证明事件。工具名和宿主支持按当前可用合同发现，不为验收强制卸载、重启或打断其他任务。新建用户任务须有工具要求的明确授权，不能从可创建或验收目标推定授权。发送回执不代替目标接收、生命周期及规则采用的核验。

[Hook 合同](https://learn.chatgpt.com/docs/hooks#sessionstart) 的 `source` 枚举和框架 matcher 不能证明每个宿主都提供对应操作。已核实当前版本没有正常入口时，明确该版本的支持边界，对应自动注入、版本核对及规则采用保留未运行；仅缺少入口证据时保留未知，先核现有原生能力，不据此断言不支持或重复要求用户代操作。

界面上的新建、恢复或清空动作，与 `SessionStart` 的 `source` 分别核对。桌面 `/new` 进入空白聊天后，若原生记录为 `startup`，只据此证明该空白聊天入口，不能改记为 `clear`；把 `/new` 当普通文字发到原聊天也不证明发生了生命周期事件。清空输入框、终端显示或未读标记均不等于清空会话。CLI、桌面及其他宿主的记录不互相代签；有正常入口时，以同一原生回合的实际事件、注入内容及模型使用验收，不能用私有协议调用或构造事件代替。

`install-hook --native-cli <已核对的 Codex 可执行文件绝对路径>` 在实际 Codex home 的 `hooks.json` 合并一个 `SessionStart` handler，匹配 `startup|resume|clear`，保留其他 Hook。CLI 路径保存在该节点 `framework-sync/native-client.json`，不进入 Git。先从当前宿主正常 CLI 及其 `app-server` 协议核实工具直调、临时上下文和退出行为；不能假定其他宿主或版本也支持。未配置入口时只返回本地核对及发布 UNKNOWN，不声称启动同步已完成。

入口直接调用现有 `sync-status` 逻辑和原生 GitHub 读取工具，再复用 `refresh` 的完整快照、共同基线、并发保护及冲突处理。原生读取通过一个短时 `ephemeral` 工具上下文完成：没有用户提示、模型回合、会话持久化、递归 Hook 或独立 worker，不读写业务数据、不复制凭据。读取既有连接的 `structuredContent`，不能把普通文本 `Action completed.` 当成版本。原生失败再用已有本机 Git；两边失败保留现用规则，发布状态为 UNKNOWN，不阻断无依赖工作。

版本未变时复用完整已校验缓存，不拉全套正文或重装；仍实际比较部署文件。版本变化时从同一个 SHA 取完整发布树，只复用 blob 一致的缓存，其余读取后整体校验。Hook 只刷新白名单正文，不从文档快照执行代码；运行版本不同或更新未完成会明确出现在实测结果中，由维护任务沿原安装能力处理。

全局 `AGENTS.md` 通常已经由 Codex 原生指令链装入；无变化时不重复注入整份规则。入口比较读取远端前后的实际部署正文；即使另一启动先完成刷新，本轮也交付发生变化的 Markdown，保留用户规则原有优先级。输出最多 64 KiB，超出部分明确列为未注入，不能冒称已采用；模型仍按当前需求读取适用 Skill。原生记录中的指令链、Hook 正文与实际文件比对，才能证明本轮取得哪一版；程序读文件本身不证明模型采用。原生读取有限时，临时进程使用独立进程组，正常或异常退出均清理所属工具子进程；不注册 `UserPromptSubmit`、`Stop` 或轮询，也不匹配 `compact`。

首次启用或定义变化须通过 [Codex 原生 Hook 信任界面](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks) 审阅。CLI 使用 `/hooks`；没有完成原生信任和真实启动验证时，分别报告这两个缺口，不能仅凭手动运行脚本宣称自动触发成功。安装器不改写信任库或开启绕过选项。框架工具升级后，从已核对的发布 Git 提交运行明确的 `install --revision <SHA> --expected-runtime <已观察值或none>`；稳定 loader 与现有本框架 Hook 迁到受管理版本入口，再核对原生信任。共享文档刷新不完成程序升级。

## 正文版本与实际运行版本

核心产品从 `0.1.0` 开始编号，唯一声明在受管源码 `codex_framework.RELEASE_VERSION`；此前发布保持未编号。规划、加载与更新先按产品版本，完整提交 hash、树与文件 hash 仅作内容及并发校验。先使用 Hook 或现有 `sync-status` 的实际运行结果：含 `tool_version` 的已编号入口支持 `codex-framework version`；旧入口没有这个字段时保留未编号或未知，不能从新正文、发布版本或活动指针推定旧程序支持新命令。不要为查询产品版本向旧入口试发 `version`，也不必因此分析同步器源码。已编号入口的 runtime 分别给出 tool/active/document 产品版本；null 保留未编号、未绑定或未验证状态，不能套用另一对象的版本。产品版本不等于包格式或输入契约编号，也不证明模型或业务能力。

安装目标可用 `install --release-version <产品版本>`，原 `--revision` 和 `--expected-runtime` 继续约束准确内容与当前状态；产品版本不符时不准备或激活。旧调用兼容。首次升级未编号程序时使用已核对发布提交的源码入口，不让旧程序试探不支持的新参数；不借版本号扩大原仓库、分支、安装或平台权限。

`sync-status` 保留 v1 同步状态与 `expected_revision`，另返回 `document_status` 和 `runtime`：实际进程的 `tool_revision`/物理目录、指针的 `active_revision`、正文已应用版本、输入契约及本机 override。正文与运行程序版本不同是 `revision-mismatch`；已发布正文的正常更新不属于未发布本机 override，后者按当前部署共同基线和实际文件判断。正文同步 `current` 不能单独证明工具采用；运行未绑定、缺件/坏 hash、契约不兼容、源码 bootstrap 调用、仍运行旧版本或更新未完成分别报告。稳定入口启动校验失败时也报告正文与尝试的活动版本，且不导入损坏代码；`version` 读取状态失败时返回未知及原错误原因，不输出猜测的版本。

代码安装只从明确的本地 Git 发布分支头及规定模块集合取对象，并校验普通文件模式、完整性、输入契约和隔离烟测；普通 `refresh` 快照仍只承载原白名单正文，不能加入脚本获得执行权。源码未提交差异不被打包或重置；若其中有应发布成果，先按当前目标整合并独立验证，而不是把它们当作已发布输入。

完整运行包、原子指针、更新恢复与回退命令见仓库 README 的“固定版本运行与恢复”。运行安装发现正文冲突时保留原活动入口和本地成果，已有正文更新仍可交付无冲突部分，独立检查仍可执行。真实安装、Hook 原生审阅、实际冷启动与模型采用分别验收；本地隔离回归不能代替它们。
