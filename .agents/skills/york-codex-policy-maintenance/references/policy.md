# 规范维护说明

<!-- POLICY_OWNER: codex-policy-maintenance -->

维护首先保证规范支持完整满足用户需求，再减少重复判断和工作耗时。现有结构、最小改动及复用偏好不能缩减需求或保护早期实现缺陷；必要改造按预期结果决定，兼容与验证覆盖实际受影响的行为。用户偏好放全局入口，专业方法放对应 Skill，项目事实放仓库；发现入口提供引用即可。

规范与方法由所属 GitHub 项目维护和发布，Mac mini 等节点加载部署副本并保存自己的实际数据。来源权属不建立额外权限体系；规范提供偏好及可选方法。目录、分支、任务关联和工作笔记属于记录；历史归属、签名、版本、审批台账、检查点或审计状态均不阻止普通工作。系统、开发者、当前用户指令和原生工具合同继续决定权限。

修订在所属项目检出中进行，按该项目授权发布后刷新部署副本。`keep-local` 或同步冲突是未发布修改受保护的状态，不是允许长期维护另一套规范；将框架修订归回 GitHub，将设备配置归回节点说明。GitHub 来源不可用时保留现用版本与修改，继续无依赖工作。具体刷新与当前任务重读见 [框架同步方法](framework-sync.md)。

根据当前问题选取有关文件并直接修改，按需要核对引用和实际使用结果。不存在必须先建候选树、比较整树指纹、提交迁移收据、启动独立代理、执行固定审计脚本或证明重新加载的阶段。专业方法也不串成固定前置。

同一要求反复失效时，先从用户要解决的问题定位需求如何被误解、转译或缩小，原地修正对应说明和错误推导，避免只追加同义规则。最小改动、复用字段、少改结构和局部修改均以完整满足需求为前提；检查相关条款是否把实现偏好或数据关系、结构、职责分析变成需求限制或执行门禁，将由此造成的缩减、重新解释、验收降级和必要修改被阻断作为需求实现缺陷修正，同时保留避免无关重构的要求。明确冲突按 [任务对齐](../../york-task-alignment/SKILL.md) 提示有依据的风险并推进，不将未核实的推断当作冲突，也不将风险提示改为统一审批步骤。资料发现、适用范围和引用问题按实际原因处理；任务开始无需用户提供特定项目、路径或 Skill 名称，目录只用于定位资料。

长期契约、当前实现或资料覆盖、单轮任务范围分别表达。“本期不做”等历史范围不写成永久业务限制；已有覆盖不冒充全量支持，具体缺口也不等于禁止后续处理。适用说明写明可识别的业务问题、材料用途及读取条件，覆盖实际不同的需求分支，合并只换说法的同义触发词。资料未被发现时先修入口，不把整份正文搬入全局规则。

同一概念的定义、适用条件和例外放在所属正文相邻位置，索引只引用；各任务共用的信息留在入口，仅部分情况需要的细节通过带条件的引用展开。设计决定确有真实取舍、改变代价较高且后续读者容易误解时，在对应业务文档中简述已知备选、选择原因和接受的限制。只记录有依据的理由，不推测历史意图，不为普通局部改动要求另建 ADR。

大类只有 code/名称或示例时，在所属公共 mapping 补齐范围、对象、关系、依据和缺口；已确认语义仅留在 README、Handler 或会话时归回 mapping。资料被应用解析时修复实际消费者，具体资料方法见 [三方资料](../../york-provider-docs/SKILL.md)。

纠偏后从修正后的需求理解继续完成具体工作，调整受错误前提影响的方案、代码、文档和测试预期，保留其他有效业务目标与累计成果，撤回已失效的实现。验收依据保持为用户当前有效要求，测试预期应覆盖这些要求，不能跟随简化后的实现下调。检查和测试用于验证需求落实结果，不替代业务理解，测试通过不证明需求完整；验证范围按实际变化选择，只说明实际完成的验证，不新增强制脚本、加载证明或任务门禁。用户要求先修工作流再处理业务时，继续仍获授权的业务工作，不以台账或复盘报告替代实施。

旧守卫脚本和其专用测试从活动 Skill 路径退役，历史副本仅用于恢复和理解旧记录；不返回虚假的 PASS，也不把旧规则迁移成另一套门禁。历史迁移说明不再作为当前执行规则。

用户要求仅保留偏好时，避免把单次经验重新写成强制限制。业务测试、文件读取和必要内容保护依具体任务选择，结果通过后无需为流程重复验证。

## 缺陷与防误用案例

本节保留可复用的误用原因与验收场景，具体机器配置、任务记录、运行数据和验证日志留在执行环境。案例用于检查正文是否足以指导正确行为，不增加每次任务的固定流程或执行门禁。

### CF-2026-10-07-01：局部节点限制被扩大为整个任务阻塞

分类：任务协调与说明执行偏差。平台授权拒绝本身不是缺陷，也不因设备互信或协作需要而允许绕过。

#### 现象与影响

本次反馈中，原正式执行节点在线，但当前任务接口拒绝执行；另一开发节点可在授权内修复代码、隔离测试、Docker 验证和 Git 发布，仓库连接也可处理获准产物。助手却将原节点的局部限制扩大为整个目标无法推进，过度要求用户回原机器操作，没有先完成独立可做步骤。正式采用及用户端真实报告验收因此与可继续的开发工作混为一谈。

#### 根因：已有覆盖与实际缺口

核对基线 `be3bfcc7ee9aa454c46a870a8161e888753a8023`：

- [任务对齐](../../york-task-alignment/SKILL.md) 已要求在当前工作线完成不依赖资料、登录或工具缺口的批次，不得假报完成。
- [环境发现与同步](../../york-workstation/references/environment-sync.md#入口认证与操作能力) 已要求仅暂停真正依赖失效入口的操作，并分别核验节点、权限与同名绝对路径。
- [工作站 Skill](../../york-workstation/SKILL.md) 已要求分开核验原生连接、本机进程、云端环境和 CI，不把一个入口失败扩大为整体不可用。

**助手执行偏差**：未将这些已有要求落实到本次分工，未先判断独立可完成的步骤，将“原节点的正式执行受限”推导成“全部工作必须等用户回原机”。既有规则已足以禁止这种整体阻断，不能把本次修正描述为首次获得跨机协作能力。

**说明缺口**：已有规则分散于任务对齐、认证入口和路径核验，没有相邻说明主会话如何协调固定执行机、每步输入输出与版本交接，以及 attached、connected 与执行授权的区别；“不自动切换另一条调查线”也容易被误读为同一目标必须在一台机器上完成。补齐这些关系和反例，保留原有授权边界与工作顺序。

#### 最小修正位置

| 位置 | 修正职责 |
|---|---|
| 全局 `.codex/AGENTS.md` 与仓库 `README.md` | 提供按依赖和权限拆分的核心入口，不默认一机包办。 |
| [任务对齐](../../york-task-alignment/SKILL.md) | 明确同一目标的跨节点分工仍是当前工作，限制阻塞范围和用户解除请求。 |
| [工作站 Skill](../../york-workstation/SKILL.md) 与 [多机任务说明](../../york-workstation/references/environment-sync.md#按依赖拆分多机任务) | 按需发现正文；集中说明执行机、版本、交接、权限变化和生产状态边界。 |
| 本说明的维护正文与缺陷案例 | 留存执行偏差和说明缺口的区别，用下列案例防止重复误用。 |

#### 场景级验收 A–E

场景中的授权仅为验收前提，不授予当前任务额外权限。逐项检查分工决定、暂停范围、产物身份与报告是否符合正文；这是静态/场景级验收，不能证明真实多机生产执行或报告送达完成。

| 案例 | 输入条件 | 应有分工与结果 | 不合格行为 |
|---|---|---|---|
| A：原执行机不可用，开发机可用 | 原节点持有正式状态且当前不可执行；开发节点输入充分，并已获修复、隔离测试、Docker 验证和 Git 发布授权。 | 开发节点继续这些步骤，交付对应版本及验证结果；原节点正式采用、调度执行与用户端真实报告验收暂停。仅请求恢复该阶段必要的授权与节点输入，收到更新后复核。 | 将整项任务停住；要求用户先回原机才能开发；将开发测试或 Git 发布当作正式采用、真实报告送达。 |
| B：切换 attached | 会话附着到另一已授权节点；既有任务与业务仍在原节点。 | 分别核实任务实际执行机，按依赖继续可做步骤；既有任务、生产状态、调度与凭据保持原归属。 | 声称 attached 切换已迁移任务或业务；因切换擅自复制状态、启动替代调度。 |
| C：两节点同名目录但版本不同 | 两节点路径文字相同，实际提交或未提交差异不同。 | 通过获准 Git/Library 交接，核对仓库与提交 SHA，或文件 ID、版本及必要内容校验；测试结果只归属实际被测版本，匹配后才被依赖步骤采用。 | 把同一路径当共享磁盘；用另一版本的结果宣布当前版本已验证。 |
| D：真实授权拒绝 | 节点 connected/在线，任务接口仍拒绝；用户称设备互信。 | 保留拒绝，仅暂停依赖该节点权限的步骤；其他已授权工作继续。权限更新后核实目标操作是否恢复。 | 用 SSH、其他入口或另一任务绕过撤权；把在线、attached 或互信当成执行授权。 |
| E：全部必要依赖不可用 | 剩余步骤的必需输入、状态或授权全部不可取得，且无获授权替代路径。 | 明确受阻步骤、已完成部分、当前无可继续步骤及最小解除条件；保留已有成果，不假装推进。 | 笼统取消整个目标；以反复重试、无关输出或未经验证的结果冒充进展。 |

规范修正、文档/分发测试通过、Git 发布、节点采用和真实业务验收分别成立；验证结果只报告实际完成的层级。
