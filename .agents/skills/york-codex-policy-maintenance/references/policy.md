# 规范维护说明

<!-- POLICY_OWNER: codex-policy-maintenance -->

维护首先保证规范支持完整满足用户需求，再减少重复判断和工作耗时。现有结构、最小改动及复用偏好不能缩减需求或保护早期实现缺陷；必要改造按预期结果决定，兼容与验证覆盖实际受影响的行为。用户偏好放全局入口，专业方法放对应 Skill，项目事实放仓库；发现入口提供引用即可。

规范与方法由所属 GitHub 项目维护和发布，执行节点加载部署副本并保存自己的实际数据。来源权属不建立额外权限体系；规范提供偏好及可选方法。目录、分支、任务关联和工作笔记属于记录；历史归属、签名、版本、审批台账、检查点或审计状态均不阻止普通工作。系统、开发者、当前用户指令和原生工具合同继续决定权限。

修订在所属项目检出中进行，按该项目授权发布后刷新部署副本。`keep-local` 或同步冲突是未发布修改受保护的状态，不是允许长期维护另一套规范；将框架修订归回 GitHub，将设备配置归回节点说明。GitHub 来源不可用时保留现用版本与修改，继续无依赖工作。具体刷新与当前任务重读见 [框架同步方法](framework-sync.md)。

根据当前问题选取有关文件并直接修改，按需要核对引用和实际使用结果。不存在必须先建候选树、比较整树指纹、提交迁移收据、启动独立代理、执行固定审计脚本或证明重新加载的阶段。专业方法也不串成固定前置。

同一要求反复失效时，按 [综合对齐](../../york-task-alignment/SKILL.md#反复纠偏时扩大范围综合对齐) 扩大比较需求历史、更早版本和相关实现，将原有范围与方案本身纳入复核，定位需求如何被误解、转译或缩小，原地修正对应说明和错误推导，避免只追加同义规则。最小改动、复用字段、少改结构和局部修改均以完整满足需求为前提，不能压缩必要的理解与比较范围；检查相关条款是否把实现偏好或数据关系、结构、职责分析变成需求限制或执行门禁，将由此造成的缩减、重新解释、验收降级和必要修改被阻断作为需求实现缺陷修正，同时保留避免无关重构的要求。明确冲突按 [任务对齐](../../york-task-alignment/SKILL.md) 提示有依据的风险并推进；未经核实的推断不得决定后续实施，按下节区分补证与实施决定，不将风险提示改为统一审批步骤。资料发现、适用范围和引用问题按实际原因处理；任务开始无需用户提供特定项目、路径或 Skill 名称，目录只用于定位资料。

框架维护对可复用缺陷的结束负责，不止于提交修订：先从原任务核对最新有效目标、原失败及可继续步骤，再查规范发现、实际消费入口、检查器能力、节点事实和分发采用的因果关系。主会话只协调与本次目标有已证关系的任务和交接；框架、系统实现及数据节点各交付其拥有的版本、原生结果与真实节点效果，由框架维护核对能否共同满足原目标。某组件未获权限或原件暂不可得，仅暂停依赖它的动作，说明恢复条件，继续其他获准工作；平台拒绝无新相关事实时不换入口重试。局部修复通过后同类偏差复现，重开系统级原因审查并保留有效修复，不以新增同义规则或测试数关闭。

联合回归从真实决策边界取输入，不把表格变成每次任务的门禁：

| 输入组合 | 可接受结果与证据边界 |
|---|---|
| 转交含较早目标，原任务后来收到新的直接目标或纠正 | 先以新要求确定本轮产出，说明旧目标是否仍待处理；原生消息顺序只提示复核，语义仍由模型判断。旧目标的静态测试通过不算本轮验收。 |
| 本机服务标为开发用途且属于独立 Compose，多个任务或业务可共享实例 | 分别核对管理归属、消费者、数据与权限隔离、容量、故障影响及恢复；标签不推导另一负责人或强制独立实例，允许共享也不强制合库。节点运行事实未取得时只暂缓有影响的动作。 |
| 一个有副作用动作被平台明确拒绝，另有消费者只读检查未执行 | 原拒绝无新相关事实不得通过其他入口或再次上传；只读步骤保持待做并继续获准工作，不写成已阻断或已完成。交接保留两者的原生状态。 |
| 局部修正及测试通过，随后同类判断再次偏移 | 保留有效修复并重开系统级原因审查；对照原失败、关联路径、发布安装版本、任务实际读取、节点效果及后续接续，缺一环只报告已证阶段。 |

长期契约、当前实现或资料覆盖、单轮任务范围分别表达。“本期不做”等历史范围不写成永久业务限制；已有覆盖不冒充全量支持，具体缺口也不等于禁止后续处理。适用说明写明可识别的业务问题、材料用途及读取条件，覆盖实际不同的需求分支，合并只换说法的同义触发词。资料未被发现时先修入口，不把整份正文搬入全局规则。

同一概念的定义、适用条件和例外放在所属正文相邻位置，索引只引用；各任务共用的信息留在入口，仅部分情况需要的细节通过带条件的引用展开。设计决定确有真实取舍、改变代价较高且后续读者容易误解时，在对应业务文档中简述已知备选、选择原因和接受的限制。只记录有依据的理由，不推测历史意图，不为普通局部改动要求另建 ADR。

大类只有 code/名称或示例时，在所属公共 mapping 补齐范围、对象、关系、依据和缺口；已确认语义仅留在 README、Handler 或会话时归回 mapping。资料被应用解析时修复实际消费者，具体资料方法见 [三方资料](../../york-provider-docs/SKILL.md)。

纠偏后从修正后的需求理解继续完成具体工作，调整受错误前提影响的方案、代码、文档和测试预期，保留其他有效业务目标与累计成果，撤回已失效的实现。验收依据保持为用户当前有效要求，测试预期应覆盖这些要求，不能跟随简化后的实现下调。保留造成纠偏的原失败输入和应有结果；修正后在相同条件或安全隔离的等价条件下复测，再核对受影响路径及实际采用版本。行为尚未重验时只说明规范或静态测试的完成范围，不写成原缺陷已修复。检查和测试用于验证需求落实结果，不替代业务理解，测试通过不证明需求完整；验证范围按实际变化选择，只说明实际完成的验证，不新增强制脚本、加载证明或任务门禁。用户要求先修工作流再处理业务时，继续仍获授权的业务工作，不以台账或复盘报告替代实施。

升级带来内容或数据契约变化时，验收须从实际持久旧对象进入新版本读、复核、写及恢复路径，并核对身份、原始时钟、不可变字段和后继消费者。只用新版本新建数据的成功测试不能证明升级兼容；旧对象缺少新字段时先区分“保留为旧语义可读”和“形成新的受验证结论”，不能靠回填推测字段、降级整个新契约或跳过完整链。旧对象通过首个检查点后仍须核对其后继独立引用和实际整轮结果，不把局部通过写成全部完成。具体项目原失败与输入留在所属项目和工作站。

旧守卫脚本和其专用测试从活动 Skill 路径退役，历史副本仅用于恢复和理解旧记录；不返回虚假的 PASS，也不把旧规则迁移成另一套门禁。历史迁移说明不再作为当前执行规则。

用户要求仅保留偏好时，避免把单次经验重新写成强制限制。业务测试、文件读取和必要内容保护依具体任务选择，结果通过后无需为流程重复验证。

## 依据与决定

检查规范时看它如何让模型作出决定，不按“可能”“假设”等词机械删改。把未经核实的猜测用于确定实施计划、代码修改、数据处理、兼容措施或扩大实施范围，属于严重缺陷；即使标注为风险、写入方案或由构造测试通过，也未取得实施决定依据。假设可以帮助提出待验证问题、选择取证入口和开展查证比较，不能预先决定验证后的处理。反复纠偏本身就是扩大比较、重新检查范围的依据，无需先证明范围外存在缺陷；禁止猜测实施不能成为限制查证范围的理由。已有契约、源码、配置和实际数据足以支持结论时直接推进；事实缺口只影响依赖它的决定，不变成所有工作等待验证的门禁。

规范、模板和专业方法相互引用同一边界：已确认决定说明适用依据；待验证问题说明缺失的事实、受影响的决定及下一取证入口。用户目标和明确设计选择可以规定未来行为，不能据此断言现行系统或第三方已具有该行为。数据或运行语义无法由现有材料确定时，沿真实匹配、写入及消费路径核对，按需要在工作站复制必要数据隔离验证。查证比较须回答未决问题，既有范围是否遗漏完整需求本身也是问题；反复纠偏时不能只因当前局部正确就停止，须足以解释偏差、确认需求覆盖与必要修改。确实取不到证据时保留缺口并继续独立工作，不用猜测补齐方案，也不让用户选择哪个未经核实的事实为真。

修正时沿原始判断→计划/交接→前置依赖→消费任务的实际记录追踪：记录每次转述保留或丢失了什么来源与状态，分别判断事实、假设、未知和可选防护。已有禁止条款仍复现时，不预断为缺提示、具体代码或模型内部故障；分别核对读取、采用、指令生成、检查器覆盖和验收。修正依赖该前提的决定、实现、文档与测试预期，撤销仅由错误前提支撑的处理，保留已确认需求及另有依据的安全限制。直接用户纠正按适用范围更新来源与下游，须回收活跃任务实际采用和错误步骤退出证据；没有实际传播或组合复验则保留未验，不能靠有限测试签永不复发。关于当前配置、启用条件、资料缺失和历史状态的修订，先核实对应对象与适用范围，不能把一次观察推广成长期能力限制。示例只用于检验规则是否清楚，不增加每次任务的固定测试流程。

## 缺陷与防误用案例

本节保留可复用的误用原因与验收场景，具体机器配置、任务记录、运行数据和验证日志留在执行环境。案例用于检查正文是否足以指导正确行为，不增加每次任务的固定流程或执行门禁。

### 缓解与根因修复的验收

治理共享执行资源的内存问题时，分别核实宿主故障、具体分配组件、目录枚举规模、备份结构和重复访问。硬链接节省物理字节不等于减少枚举请求；将集合溢写到磁盘的隔离内存改善也不证明原规模的文件共享负载、日常扫描必要性或备份读取已修复。区分有效保护、恢复与尚未解除的结构性原因；具体事故数据和节点证据留在所属项目及工作站。

对存储问题，先确认业务为何需要该频率和精度，区分权威原文、引用、物化、备份与派生统计；再在实际数据关系和访问层消除无谓工作。目标按业务规模、既有指标及安全受控阶梯说明扫描/查询次数、重复率、内存和 IO 增长、延迟、一致性及恢复；行业合理性结合该业务的恢复与统计需要判断，不编造单一阈值。外置存储若是长期合理的数据结构，应说明预期规模、资源边界和清理时机，并在原工作负载的安全隔离等价条件下证明问题解除；不机械禁止分层存储。以下决策场景用于检验职责，静态检查本身不能代替实际行为复测，也不要求制造生产压力。

| 已有证据 | 结论与后续 | 不合格结论 |
|---|---|---|
| 已隔离故障或将集合溢写，原内存峰值受控；扫描触发与增长机制仍未知 | 标为缓解，保留有效止损，沿现有调用与有限样本查明原因；不以磁盘承接增长关闭缺陷。 | 内存不再溢出就宣布百万文件扫描已根治。 |
| 已证明扫描频率、数据结构和生命周期符合业务约束，分层存储有明确容量与清理边界；修后原场景和相关路径满足目标 | 可将分层存储作为充分的长期修复，说明为何原问题已解除及验证覆盖。 | 一概禁止外置存储，或只凭小样本单测宣布充分。 |
| 查明并消除不必要的重复扫描或无界保留，受影响路径在目标规模下复测通过 | 标为已修复，保留必要的资源保护措施。 | 只记录原因却不修改，或用提交、通用测试和关闭记录代替复测。 |
| 已证明服务恢复或重试成功，但重复负载机制仍存在 | 只解除有界瞬时故障的执行阻断；结构缺陷继续处理。 | 把进程重启、调大资源、换存储或第二轮成功记为根因修复。 |
| 根因事实仍不足，隔离取证也无法回答当前问题 | 标为待定位，继续独立可做工作；不凭猜测追加存储、扩容或宣布完成。 | 无限扩查，或把未知原因写成已解决。 |

### 局部能力限制与依赖分工

可连接、已附着和目标动作获准分别核实。将原目标拆成实际需要的输入、执行、版本交接及验收依赖；一个节点或入口受限只限制对应依赖，其他获准开发、验证和交付继续。已有规则未被采用与说明本身缺项分别查证，不能把局部修订写成首次获得能力。

下列为通用决策场景，授权仅为输入前提，不授予当前任务新权限；静态或隔离场景不证明真实节点采用及业务结果。

| 案例 | 输入条件 | 应有分工与结果 | 不合格行为 |
|---|---|---|---|
| A：原执行机不可用，开发机可用 | 原节点持有正式状态且当前不可执行；开发节点输入充分，并已获修复、隔离测试、Docker 验证和 Git 发布授权。 | 开发节点继续这些步骤，交付对应版本及验证结果；原节点正式采用、调度执行与用户端真实报告验收暂停。仅请求恢复该阶段必要的授权与节点输入，收到更新后复核。 | 将整项任务停住；要求用户先回原机才能开发；将开发测试或 Git 发布当作正式采用、真实报告送达。 |
| B：切换 attached | 会话附着到另一已授权节点；既有任务与业务仍在原节点。 | 分别核实任务实际执行机，按依赖继续可做步骤；既有任务、生产状态、调度与凭据保持原归属。 | 声称 attached 切换已迁移任务或业务；因切换擅自复制状态、启动替代调度。 |
| C：两节点同名目录但版本不同 | 两节点路径文字相同，实际提交或未提交差异不同。 | 通过获准 Git/Library 交接，核对仓库与提交 SHA，或文件 ID、版本及必要内容校验；测试结果只归属实际被测版本，匹配后才被依赖步骤采用。 | 把同一路径当共享磁盘；用另一版本的结果宣布当前版本已验证。 |
| D：真实授权拒绝 | 节点 connected/在线，任务接口仍拒绝；用户称设备互信。 | 保留拒绝，仅暂停依赖该节点权限的步骤；其他已授权工作继续。权限更新后核实目标操作是否恢复。 | 用 SSH、其他入口或另一任务绕过撤权；把在线、attached 或互信当成执行授权。 |
| E：全部必要依赖不可用 | 剩余步骤的必需输入、状态或授权全部不可取得，且无获授权替代路径。 | 明确受阻步骤、已完成部分、当前无可继续步骤及最小解除条件；保留已有成果，不假装推进。 | 笼统取消整个目标；以反复重试、无关输出或未经验证的结果冒充进展。 |

规范修正、文档与分发测试、公开发布、节点实际加载和真实业务验收分别成立；只报告实际完成的层级。

### 字段影响、假设与实施决定

字段变化是否导致删除重建或需要兼容处理，按实际匹配键、写入语句、约束和消费者核对。比较查证与据此实施分别判断；假设可以指导取证，不预先决定改造。下表为通用场景，构造测试不证明真实业务前提已经成立。

| 输入条件 | 应有决定 | 不合格行为 |
|---|---|---|
| 已证实有影响 | 根据实际触发条件与影响，确定满足需求的修改及针对性验证。 | 将局部影响泛化到其他对象或附带无依据的兼容措施。 |
| 同一疑点已证实无影响 | 撤销该猜测及依赖它的额外步骤，按已确认需求继续。 | 仍为已被否定的影响保留特殊处理或重复比较。 |
| 关键证据不足 | 只安排能区分疑点的必要取证；仍取不到时保留该决定的缺口，继续独立工作。 | 先按猜测实现、选择默认值，或让用户把猜测选成事实。 |
| 已有适用契约和源码足够 | 直接作出有依据的决定，无需再复制数据或重查全链路。 | 将本地回放、双库比较或线上取证设为固定前置。 |
| 构造测试通过但实际前提未确认 | 仅确认所构造条件下的行为；按契约或用户目标验证新行为时说明该依据。 | 以测试通过证明实际前提成立、线上已发生或兼容改造必需。 |

### 反复纠偏时的综合对齐

以下场景检验 [任务对齐](../../york-task-alignment/SKILL.md#反复纠偏时扩大范围综合对齐) 是否能重新识别范围，不建立固定分支、回溯次数或每次任务的检查流程。

| 输入条件 | 应有决定 | 不合格行为 |
|---|---|---|
| 当前修改点正确，但同一需求仍被反复纠偏 | 从完整需求检查其他业务路径、上下游和最终结果，主动发现原范围遗漏的模块或仓库。 | 只检查当前 diff；要求先证明范围外有缺陷才扩大比较。 |
| 多轮修改沿用同一错误前提 | 综合回读原始需求、有效纠偏、历史方案、修改前及演进版本，重新确定完整方案。 | 只从当前代码推测必要性，或只看上一轮改动继续补丁。 |
| 项目使用不同分支、标签或提交作为参考 | 按实际任务选择适用来源，指定来源纳入综合比较，继续核对需求覆盖。 | 固化某个分支名或版本入口，或把指定来源当成比较范围上限。 |
| 历史实现与当前有效要求冲突 | 用历史解释演变，按有效要求及核实事实修正方案和测试预期，保留其他有效成果。 | 因历史更早就照搬旧实现，或整体回滚有效改动。 |

### 操作与交接的范围边界

跨任务消息、优先级调整、暂停与写入都属于需要核对范围的实际动作。同领域、同仓或路径相似不等于同一个目标；依据当前有效要求、已证依赖、拟影响对象和实际结果判断。消息受理只证明接收该指令，不证明暂停时长、执行效果或结果已核收。

只检查正文或分发测试不证明模型在真实运行中作对决定。隔离验证不向真实在途任务发送演练消息，也不改变正式状态。

| 输入与状态 | 应有决定和可观察结果 | 不合格行为 |
|---|---|---|
| A 正在重构；同领域的独立只读问题随后到达，未要求改变 A | 当前会话只读取证或单独核对；不向 A 发消息，A 的优先级、阶段和写入集不变。 | 把核对投递给 A，要求优先处理或暂缓改动。 |
| A 的同一缺陷收到新事实或用户明确纠正 A 的方案 | 在 A 续办并只修正受影响步骤，保留有效成果；明确纠正可立即 steer。 | 每次新建任务而丢失故障上下文，或用防干扰规则拒绝纠正。 |
| 有证据表明 A 即将执行未授权真实写入 | 立即止住受影响路径并核实风险，其他安全工作继续。 | 排队等待而放任风险，或泛化暂停所有工作。 |
| 当前目标确需另一任务的稳定产物；其余步骤独立 | 复用有版本的成果或有界交接，只暂停依赖该输入的步骤；独立步骤继续。 | 未证依赖就改变对方优先级，或让整个目标等待。 |
| 两项任务在同仓，但修改对象不同；之后发现同文件或同语义写入冲突 | 无冲突部分并行；重叠写入按版本串行或由一方集成，保持单一实际写入责任。 | 整仓独占，或两个写入者互相覆盖。 |
| 实施中发现与本次目标无已证关系的邻近缺陷或重构机会 | 留下证据与建议，不顺手实施或 steer；完整目标确需的跨文件改动仍推进。 | 借“同仓”“顺手”扩项，或机械要求每个必要内部改动重新授权。 |
| 修正后仅有文档检查、模拟重放或发布记录，真实任务尚未采用 | 分别报告静态、隔离行为、发布及采用的证据和缺口；不声称原事故已闭环。 | 以规则文字、构造测试或 Git 推送替代采用版本的原场景复测。 |

### 局部验收、实际采用与完整目标

局部规则、合成测试或安装通过后仍发生同类偏差，应保留有效部分并核对原失败、实际读取、采用版本、执行结果和未完成依赖。不能用分项通过关闭系统目标，也不因后续无关工作未完成扣住已成熟成果。解析器只处理实际提供的输入，字段齐全、状态返回或空步骤不证明来源完整及真实工作完成；按实际任务契约和独立验收适用性核对。

资源标签、使用者、管理归属、数据权限、物理实例、容量和故障影响分别判断，技术用途不推导另一负责人。默认沙箱、网络或认证错误先归属于准确入口和动作，不冒认全局权限撤销；真实平台拒绝仍保留准确效果边界，不换通道绕过。实施者不自签适用的独立验收，复核须绑定确切代码、输入、环境及判据，具体结果和修订沿原任务保留。

主线目标与领域结果不能被局部预检、资源子问题或检查器修复替代。助手在新问题、纠偏、失败及分项验收后回看完整有效目标，组织已有职责的授权交接、回收结果并推进可继续工作；具体项目、任务清单和运行状态留在原持久入口，不另建中央协调层。

具体事故原文、任务与提交沿革、节点配置、运行验证和未完成事项由助手侧原任务或工作站保存、发现和维护。共享方法保留可复用约束及场景；公开产品的版本兼容和接口契约仍由所属仓库正常维护，不将所有历史说明一概视为秘密，也不把历史记录当作当前状态或执行许可。

| 输入 | 预期决定 |
|---|---|
| 服务仅被 README 标为“开发环境”“独立 Compose”，无另一负责人原生证据 | 不推出另一负责人；工作站数据节点管理责任不因技术用途转移。 |
| 未知 StarRocks/MySQL 的消费者、负载和恢复条件 | 先在已授权范围核对依赖、实际负载、隔离和恢复条件；未证实前不决定停服。 |
| 一项副作用遭平台拒绝，同时日志读取和独立诊断获准 | 保留原拒绝且不换入口重试，继续可做检查；不宣布全部资源管理停工。 |
| 已授权维护涉及重要数据删除、真实服务中断或新的目的地 | 自主分析与可恢复维护继续；具体不可恢复删除、实际业务中断或平台逐次确认仍按原授权与平台规则限定。 |
