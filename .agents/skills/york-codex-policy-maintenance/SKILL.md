# York 规范维护

全局保存稳定用户偏好，Skills 提供可选专业方法，仓库保存业务契约和事实。共享框架由 GitHub `york6668/codex-framework` 持有、维护和发布；BTC 专属方法归 `york6668/btc-core-strategy`。Mac mini 是数据存储与执行节点，其全局文档和 Skills 是部署副本。

长期修订在所属项目的检出中修改正文及引用，按该项目授权发布，再刷新受影响的部署副本与当前任务上下文；当前用户要求立即生效。发现仅存在于部署副本的修订时，保护并明确标为未发布修改，归回所属项目；设备配置和历史数据留在节点，不将本机差异维持成独立规范来源。GitHub 项目发布与 Codex 云端执行环境发布是不同操作。

- 保留能帮助用户完成工作的偏好与方法，删除自建审批、目录绑定、强制守卫和固定记录流程。
- 删除守卫、绑定或固定流程时，保留它们承载的有效用户要求，包括修改范围、兼容性、完整满足需求前提下的最小改动及交付后的可用状态，并用直接的行为或结果表述承接，避免随旧机制一起删除。复用和少改的前提应与偏好写在同一条款中；实现偏好及数据关系、结构、职责分析均不能转译成缩减、重新解释需求、降低验收标准或阻断必要修改的规则。保留明确冲突时提示风险并推进的处理方式，不把风险提示变成统一审批前置。这些要求不需要另建脚本、审批或台账来落实。
- 修改范围依据当前请求；不要求候选树、整树指纹、独立代理、审计 PASS、强制测试清单或加载证明。
- 按需求与受影响行为核验正文、引用和实际使用结果，验证规模与变化相称；发现旧规则导致的方案或测试预期缺陷时一并修正。覆盖充分后减少重复验证，不能以改动小或旧测试通过代替需求验收。
- 将未经核实的猜测用于确定后续实施计划、代码、数据处理、兼容措施或额外比较，属于严重规范或执行缺陷；只要求“标明不确定性”不足以修正。原位区分用于补证的待验证问题与有依据的实施决定，检查模板、引用和测试预期是否继续沿用错误前提；保留必要取证及有依据工作的自主推进，不新增统一审批或验证门禁。方法与场景见 [维护说明](references/policy.md#依据与决定)。
- 历史记录保留参考价值，过期规则退出活动入口，不因历史检查点或工具约束阻止当前工作。
- 长期正文记录已核实能力、条件及适用边界，当前环境的开关快照、临时缺配置和本轮进度不提升为长期能力限制。纠偏时修正产生误判的规则和引用，不仅追加针对单个现象的例外。
- 配置、记忆、业务仓库和外部操作按用户实际请求处理，本 Skill 不扩展授权。

启动检查、用户要求刷新或长期规范发布后，使用 [框架同步方法](references/framework-sync.md)；普通追加消息不触发同步。

需要定位正文时参考 [内容索引](references/policy-owners.yaml)；调整触发条件、信息组织或设计取舍说明时参考 [维护说明](references/policy.md)。完成相关修正后继续原业务工作，简明告知实际变化即可。
