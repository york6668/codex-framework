# 工作区与交付方法

<!-- POLICY_OWNER: safe-delivery -->

以下说明代码审查方法及全局 Git 交付偏好的落实方式。工作区和操作方法按现场选择，不形成固定流程；交付目标以有效用户授权及下述默认规则确定。

## 代码审查

审查方法统一见 [需求与实现两轴审查](../../york-engineering/references/review.md)：先固定可比较内容，分别判断需求覆盖与实现质量，包含相关未提交改动。审查不增加 Git 交付授权，也不自动实施范围外建议；本文件继续负责工作区、提交内容及获准 Git 操作。

## 提交内容

执行全局偏好中的长期必要性和源码数据边界，根据实际用途核对新增、已跟踪和已暂存内容。文件是否值得留在 Git，以项目和业务的持续需要为准；本次任务是否使用、文件年代、数量、行数及历史通过记录不能单独决定去留。本次提交范围仍遵守用户授权，不能因此纳入其他工作的改动。

公司业务源码、契约说明及长期测试源码由所属公司 GitLab 仓库维护；本地检出用于开发测试，不因框架方法更新迁入 GitHub 共享框架。获准页面交付单独导出文档、页面运行资源和效果图，不能把源码目录、运行材料或实际配置整包上传。具体三件套及验收按[业务页面交付](../../york-engineering/references/business-workflow.md#前后台页面贯通与效果交付)，配置和认证发现继续按[工作站方法](../../york-workstation/SKILL.md)。

测试程序、断言和小型样本构造逻辑具备持续业务回归价值时才随源码维护，测试源码的身份本身不构成收录理由。保留保护核心业务、接口兼容及实际故障风险的测试；按业务职责合并重复覆盖、修正当前有效测试的错误预期。已失效的历史测试、一次性核验和无持续用途的调试代码直接删除，不为保留历史文件补兼容或另行归档；有效的核心业务回归由当前测试维护。不设置文件数量指标，不增加清理台账或提交门禁。

实际运行状态、测试数据文件、合成或脱敏快照、数据库、日志、凭据和机器实际配置不随源码提交或导出；一次性验证程序和结果留在执行环境。自主维护与推送授权不豁免这项边界，扩展名和“不含敏感信息”也不能单独证明文件应入库。

误入库文件先保留仍需使用的本地副本，再停止跟踪；同步修正忽略规则、导出清单和测试读取/生成位置，避免下一次生成或打包重新纳入。测试应继续覆盖原有行为，不能用跳过验证替代数据整理。正常差异审核即可，不为此新增提交守卫或审批流程。

## 工作身份与任务工作区

同一工作的累计代码和决定可以通过原记录继续定位。`work_id`、对话 ID、`resources.json` 和历史目录关联只提供线索；无需注册写入者、绑定版本或目录租约。

已有工作区适合当前修改时直接使用，需要隔离实际并行改动时可用普通 `git worktree`。物理 worktree 是可选隔离方式，正常 IDEA 项目仍是默认审核入口；工作位置与交付分支分别确定，使用 IDEA checkout 不意味着向其当前检出分支交付。

业务系统（含 platform2）的新分支只能从本次刚同步的 `origin/sit` 创建，不得从 `sitAll`、其他任务分支或未经核实的当前 `HEAD` 创建。创建前同步远端 `sit`，明确以更新后的 `origin/sit` 为起点；本地 `sit` 可能落后，仅证明 `sit` 是祖先也不能证明分支未带入 `sitAll` 的额外历史。

接续工作仅沿用已确认来源正确的基线。发现来源错误时，保护已有改动，从刚同步的 `origin/sit` 新建分支，仅迁移本任务的最终累计差异，不合并错误来源分支或复制其整树内容；不能以“接续”为由保留错误历史。旧分支是否保留、替换或删除依用户要求处理，不默认重写已推送历史。开发基线不构成交付目标授权，正确创建的任务分支不要求每次推送前重新合入 `sit`。

## 操作范围与内容连续性

以有效用户要求确定实施、提交和推送范围。接续时保留已完成的修改，不从较旧副本覆盖当前代码；有真实混合修改时按文件或差异合并。保存恢复副本可以帮助转移复杂改动，但不要求每次生成完整快照、哈希或签名。

## 物理资源与恢复

使用 Git 当前分支、工作树和文件状态定位内容。Git 自身的分支占用或文件冲突按实际原因处理。历史 App 工作目录、归档状态、旧审核绑定和检查点不形成操作限制；不为此要求旧任务 release、claim 或 archive。这不免除对 Git 实际分支检出占用的收尾处理。

工作记录可记“任务—工作区—分支—本次改动”的关系，不把正常 IDEA checkout 永久分配给某个任务。不建立 common-gitdir 自建锁、签名版本链或自建转换 wrapper。

## 审核交接

正常 IDEA checkout 是默认审核入口。若成果在 worktree 中，按需要切换已有任务分支并转移本次未提交修改；需要在另一目录检出任务分支时，先按下述收尾方法释放本任务源临时工作树的分支占用，再在审核目录检出任务分支。无需新增提交来转移分支，也无需调用 `prepare_review`。

成果放入实际审核目录后，后续修改以该目录的当前内容为准。旧副本可留作恢复资料，记录其位置即可；不把清理、冻结、签名或归档作为审核前置。

## 审核与交付证据

用户审核通过并授权后，通过普通 Git 提交和推送本次成果。仅要求修改代码或代码已准备好审核，不包含提交、推送授权。依据当前差异选择暂存内容，关注用户指定目标和实际命令结果。测试结果用简短文字说明范围及缺口；无需文件清单、逐文件校验报告、审批 manifest 或不可变交付收据。

## 推送后的本地收尾

默认提交并推送到 `york-worktree/<中文业务名称>` 后，在正常 IDEA 工作区执行 `git switch <本任务分支>`；已经在该分支则无需切换。若该分支被本任务临时工作树占用，先按下一节释放占用。

常规收尾查看一次 `git status --short --branch` 即可，不把分支对比、逐文件检查或基线重建作为必经步骤。保留其他未提交改动及暂存状态，不要求整仓干净。

只有 Git 阻止切换，或切换后仍有本任务已交付改动残留时，才针对具体文件和差异处理，不强制覆盖。用户明确要求保持原分支时尊重该要求；未能完成切换或处理残留时简明说明缺口。本地切换不包含向 `sit` 等共享分支提交、合并或推送，已有明确交付目标仍按有效授权执行。

## 交付收尾与分支占用

完成审核交接或获准 Git 交付后，默认在本任务的 Codex 临时工作树执行 `git switch --detach HEAD`，释放任务分支占用，保留该工作树的代码、未提交内容、暂存状态和目录；已 detached 则无需重复操作。只释放本任务临时工作树的占用，正常 IDEA 工作区保持在任务分支，不处理其他任务的工作树。

需要定位占用时使用 `git worktree list --porcelain`。用户明确要求保持检出，或 Git 操作受阻时保留现场并说明原因，不强制检出、清理文件或自动提交。普通进度更新、测试等待和仍在进行的开发不触发收尾。

## 目标识别与多目标交付

用户授权提交、推送但未指定目标时，默认使用本任务的 `york-worktree/<中文业务名称>` 分支。已有且来源正确的本任务分支继续使用，不重复创建；没有则按上述基线规则创建任务分支，在保护用户和其他工作改动的前提下，承载本次获准交付的累计改动。默认分支前缀为单数 `york-worktree/`。

“本任务分支”不等于当前检出分支。当前检出分支、upstream 和 IDEA 审核目录均不代表交付目标授权；即使当前位于 `sit`，普通“提交并推送”也应交付到上述任务分支，不能直接推送 `sit`。

本任务中仍有效的明确仓库和分支授权优先。推送或合并到 `sit`、`sitAll`、`master`、`staging` 等共享分支，须有明确指向该目标的授权；已有明确授权时按指定目标执行，不强制先建任务分支，不重复询问许可。默认任务分支规则已确定目标时同样自主执行，无需再询问目标。

不自动增加其他环境、制品发布或部署目标。跨仓修改按真实生产消费关系交付，不增加来源审计阶段。上述规则不要求新增守卫脚本、审批台账或固定操作流程。
