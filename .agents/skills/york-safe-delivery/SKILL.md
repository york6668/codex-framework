# York 代码审核与交付

用户优先在正常 IDEA 项目中审核完整代码，审核通过并授权后提交、推送 Git。工作区、分支和原任务记录用于定位成果，不授予整仓独占权。

审查改动或准备交付时，按 [代码审查](references/policy.md#代码审查) 核对需求实现与代码质量，实际差异包括本任务尚未提交的内容。审查本身不授权提交、推送或附带重构。

源码与数据边界同样适用于个人工具、框架和获准自主交付的仓库。按 [提交内容](references/policy.md#提交内容) 核对实际用途，覆盖新增、已跟踪及已暂存内容；IDEA 审核入口和逐次确认的例外不改变可提交内容范围。

- 根据当前文件和 Git 状态选择直接工作或 worktree 隔离，使用普通 Git 命令即可；无需调用自建守卫、申请绑定、释放旧任务的历史绑定或生成 manifest。Git 自身的分支检出占用仍按交付收尾规则处理。
- 新 platform2 工作默认以最新 `origin/sit` 为开发基线，接续保持实际基线和累计改动。开发基线不构成交付目标授权，推送任务分支不要求每次重新合入 `sit`。
- 准备审核时将本次成果放到用户实际使用的 IDEA checkout，并打开项目或相关差异。历史绑定、旧任务未归档、检查点过期和记录缺失均不阻止复用目录。
- 保留用户和其他工作的当前改动，按实际文件冲突选择合并或独立工作位置。确有同时修改同一内容的情况再协调，不因历史对话关联联系其他任务。
- 用户授权提交、推送但未指定目标时，默认使用本任务的 `york-worktree/<中文业务名称>` 分支；已有本任务分支继续使用，没有则创建，承载本次获准交付的累计改动。当前检出分支、upstream 和 IDEA 审核目录均不代表交付目标授权，当前位于 `sit` 也不能据此直接推送 `sit`。
- 本任务中仍有效的明确分支授权优先；推送或合并到 `sit`、`sitAll`、`master`、`staging` 等共享分支，须有明确指向该目标的授权，且不强制先建任务分支。普通“提交并推送”仅采用默认任务分支；目标已明确时自主执行，不重复询问许可。审核就绪不代表用户已经审核通过，仅要求修改代码不包含提交、推送授权。
- 推送成功后，在正常 IDEA 工作区直接切换到本任务分支；已在该分支则无需切换。常规收尾查看一次 `git status` 即可，保留其他改动及暂存状态，不作例行分支对比或逐文件检查。只有切换受阻或仍有本任务已交付改动残留时，才针对具体问题检查差异，不强制覆盖。见 [推送后的本地收尾](references/policy.md#推送后的本地收尾)。
- 完成审核交接或获准 Git 交付后，默认释放本任务 Codex 临时工作树对任务分支的占用；IDEA 需要检出该分支时先释放占用。保留临时工作树的代码、未提交内容、暂存状态和目录，不处理其他工作树的占用。用户明确要求保持检出或 Git 操作受阻时，保留现场并说明原因。见 [交付收尾与分支占用](references/policy.md#交付收尾与分支占用)。
- 只进行与本次修改相称的验证。默认简短告知审核路径、测试结果和需要用户决定的真实问题，不制作交付文件、校验清单或收据。

按需要参考 [工作区与交付方法](references/policy.md)。旧工具、资源绑定和操作日志仅供历史恢复，不再作为执行条件。
